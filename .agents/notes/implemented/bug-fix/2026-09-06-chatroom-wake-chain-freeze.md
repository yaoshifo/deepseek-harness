# Agent Note: Chatroom wake-chain freeze — jobs die with the epoch, supervision owns the deadline

Status: implemented

English | [中文](2026-09-06-chatroom-wake-chain-freeze.zh.md)

## Problem

The 2026-09-05/06 oc_97be4a1c chatroom run (「中国低估值股票筛选」, five roles + steward): at 00:47 the room froze and stayed frozen in `discussing` for 6+ hours. Nothing was hung — every session log ended with `turn/end completed`. The freeze was a three-layer wake-chain break. (1) The native subtask E, the actual data fetcher, ended its turn planning to be woken by its background job `bash-23` (a watchdog expected to auto-merge in ~78 minutes); turn-end settlement disposed its Activation, and owner disposal cancelled the job process tree — every data file and log stopped at the turn-end second, so the promised completion wake could never land. (2) The steward's one-shot first-turn auto-report had been consumed by a progress note ("还在等 E"); its later turns never re-reported, and the only re-arm is a parent follow-up the moderator had explicitly declined to send ("不干预、不打扰"). (3) The moderator ended its turn waiting on a push that could now never arrive, with no gather armed and no timeout anywhere. Two contract violations: the continuation manager's residency derivation ignored live background jobs (the bridge's own reaper skips `backgroundTasksPending > 0` — the main session already honored the contract), and the chatroom owned no deadline for any durable expectation of future work — those expectations lived in model prose and process memory.

## Decision

- **Residency holds for live background jobs** (`packages/subagent/subagent/src/continuation.ts`, fix `c48b659543`): live (`running`/`stopping`) jobs count toward residency exactly like undisposed children; job settlements re-observe residency through `onJobsChanged`; the registry binds via `inject` so it may load before or after the runtime. No grace period, by design: a bounded wait re-introduces killing live work (the 3600 s MCP trap's shape). A hung job is supervised by `job_kill`, a parent follow-up, or a lineage drain — which still cancels agents first, and agent disposal cancels their owned jobs through the registry.
- **A level-triggered stall supervisor owns the deadline** (`packages/acp/feishu-bridge-chatroom/src/engine/chatroom-supervise.ts`): one sweep per tick over every engine's hub↔steward relations (moderator flag + provisioned steward). A relation quiet past `assistantStallSec` (default 1800, 0 disables, non-zero floor 600 enforced at apply) gets a supervision wake carrying facts (steward name, quiet minutes, last-reply excerpt) and options (nudge with a follow-up / wrap up with delivered results / stop the room). Three layers keep a mis-set deadline from making the supervisor a nuisance: the evidence gate (open turns either side, a parked ask, pending background tasks, an armed barrier are declared waits, not stalls), the progress clock (only organic relation activity resets the episode — the supervisor's own tagged wake turns do not), and a breaker (three unanswered wakes → one visible group notice per window, plus a journal warn). Everything derives from durable `featureState` every tick: no armed timers to clear, `interruptChatroom`/end flipping the moderator flag is the stop, a daemon restart resumes by construction. An activity stamp of 0 reads as "stalled since forever", so legacy frozen rooms are picked up on the first post-deploy tick — the incident room self-heals after `/reload`.

## Alternatives considered

- **Teach `Agent.whenIdle()` about jobs** (one predicate, every consumer). Every dispose path awaits `whenIdle` before cancelling jobs, so the change would hang disposal; and the agent layer must not know the jobs capability. Wrong layer.
- **A universal durable wake ledger for all delegation shapes.** Generic subtasks have no durable "mission pending" state (only "ever reported"), so done-quiet and frozen-quiet are indistinguishable without new machinery nothing currently needs.
- **Structured concurrency — block turns while waiting.** Fights the product: groups must stay interactive during long waits, and user messages queued behind a 78-minute blocked turn are a recorded past pathology (the「已排队」symptom).
- **Prompt-level fixes** ("always arm a gather when delegating"). Advisory; prose promises are exactly what failed here.
- **Per-epoch auto-report for attended children.** Fixes one hop, adds wake noise on every progress note, and still freezes when both sides go quiet; the supervisor's nudge option re-arms the one-shot through the existing follow-up path when it matters.

## Consequences

- Tests pin: a child owning a live job does not settle (no `subagent/end`, job survives); the job's terminal record re-derives settlement exactly once; terminal-only registries settle immediately; a lineage drain still cancels the live job. Supervisor tests pin the wake message verbatim (facts + options + tag), every evidence-gate branch, episode dedupe, the breaker's notice-per-window, organic-activity budget reopen, the moderator-flag stop, and the config floor / zero-disable / default.
- The wake is a new model-visible input: it rides the existing synthetic `user/message` path (`wakeChatroomModerator`), tagged `chatroomSupervisorWake` in message metadata so activity tracking skips it.
- Coverage: mechanism A benefits every continuable-subagent consumer — any group, project, or frontend; the chatroom was merely the first fully-forensicated victim. Mechanism B covers the hub↔steward relation only: role↔assistant waits carry their own armed-gather timeouts, generic subtask parents have user-visible panels and no durable mission state, and a parked user ask is an intentional wait. A room whose steward genuinely finished but whose moderator sits quiet in `discussing` still reads as stalled — waking the moderator to drive the room forward is the intent.
- During long steward jobs the supervisor's per-deadline nudge costs one moderator + one steward turn per window; the steward's status reply resets the clock.
- Deployment: bridge rebuild + `/reload`; afterwards the frozen incident room receives its first supervision wake within one sweep tick, and journal `chatroom: supervisor woke stalled moderator` lines mark every intervention.
