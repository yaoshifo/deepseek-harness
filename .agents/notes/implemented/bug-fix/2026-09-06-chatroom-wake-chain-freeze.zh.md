# Agent Note: 聊天室唤醒链冻结——后台任务随 epoch 消亡、监督网接管期限

Status: implemented

[English](2026-09-06-chatroom-wake-chain-freeze.md) | 中文

## Problem

2026-09-05/06 oc_97be4a1c 聊天室（「中国低估值股票筛选」，五角色 + 数据管家）：00:47 起房间冻结，在 `discussing` 停滞 6 小时以上。没有任何东西挂死——每份会话日志都以 `turn/end completed` 收尾。冻结是唤醒链的三层断裂。（1）真正下数据的原生子任务 E 结束回合，计划等后台任务 `bash-23`（一个预计约 78 分钟后自动合并的看门狗）的完成通知；回合结束的结算 dispose 了它的 Activation，owner 处置随即取消其任务进程树——所有数据文件与日志停在回合结束的那一秒，承诺过的完成唤醒永远无法落地。（2）数据管家的一次性首回合自动回报已被一条进度消息消耗（「还在等 E」），后续回合不再回报，而唯一能重新武装它的父任务追问被主持人明确拒绝（「不干预、不打扰」）。（3）主持人结束回合等待一个现在永远到不了的推送，没有任何武装的 gather，也没有任何超时。两处契约违背：继续执行管理器的驻留推导看不见存活的后台任务（bridge 自己的 reaper 会跳过 `backgroundTasksPending > 0`——主会话早已遵守该契约）；聊天室对任何「对未来工作的持久期待」都不拥有期限——这些期待只活在模型散文与进程内存里。

## Decision

- **存活后台任务计入驻留**（`packages/subagent/subagent/src/continuation.ts`，修复 `c48b659543`）：存活（`running`/`stopping`）任务与未 dispose 的子级同等计入驻留；任务结算经 `onJobsChanged` 重新观察驻留；注册表经 `inject` 绑定，加载顺序自由。刻意不加宽限期：有界等待会重新引入杀活任务（3600 秒 MCP 陷阱的同型）。挂死任务的监督是 `job_kill`、父任务追问、或血缘排空——排空仍先取消各 Agent，Agent 处置经注册表取消其拥有的任务。
- **电平触发的静默监督网接管期限**（`packages/acp/feishu-bridge-chatroom/src/engine/chatroom-supervise.ts`）：每次扫描遍历所有 engine 的 hub↔数据管家关系（主持人标志 + 已配置管家）。关系静默超过 `assistantStallSec`（默认 1800，0 关闭，非零下界 600 在 apply 期强制）即收到监督唤醒——携带事实（管家名、静默分钟数、最后回复摘录）与选项（追问催办 / 用已交付结果收尾 / 停止本场）。三层设计让设错的期限不会把监督者变成麻烦：证据门（任一侧打开的回合、停驻的 ask、在飞后台任务、已武装的屏障是已声明的等待，不算 stall）、进度时钟（只有关系的有机活动重置周期——监督唤醒自身带标记的回合不重置）、熔断器（连续三次唤醒无进展 → 每窗口一条可见群通知 + journal 告警）。全部状态每次扫描都从持久 `featureState` 推导：没有待清除的武装定时器，`interruptChatroom`/结束翻掉主持人标志即停止，daemon 重启天然恢复。活动时间戳为 0 读作「自远古停滞」，遗留冻结房间在部署后的第一个扫描周期即被捞起——本次事故房间在 `/reload` 后自愈。

## Alternatives considered

- **让 `Agent.whenIdle()` 认识任务**（一个谓词、全部消费方生效）。每条处置路径都先 await `whenIdle` 再取消任务，该改动会挂死处置；且 agent 层不应认识 jobs 能力。层级错位。
- **面向一切委派形态的通用持久唤醒账本。** 通用 subtask 没有「任务未完」的持久状态（只有「曾经回报过」），不做新机器就无法区分「做完的安静」与「冻住的安静」，而当前没有消费方需要它。
- **结构化并发——等待时阻塞回合。** 与产品形态对打：长等待期间群必须可交互，用户消息排队在 78 分钟阻塞回合之后正是历史事故记录过的「已排队」病理。
- **Prompt 层修复**（「委派时永远武装 gather」）。建议性的；散文承诺正是本次失败的方式。
- **attended 子级改为每 epoch 自动回报。** 只修一跳，每条进度消息都增加唤醒噪音，且两侧都静默时照样冻结；监督网的催办选项在真正要紧时经既有追问路径重新武装一次性回报。

## Consequences

- 测试钉死：拥有存活任务的子级不结算（无 `subagent/end`、任务存活）；任务终态记录恰好重推导出一次结算；只含终态记录的注册表立即结算；血缘排空仍取消存活任务。监督网测试逐字钉死唤醒消息（事实 + 选项 + 标记）、每个证据门分支、周期去重、熔断的每窗口一条通知、有机活动重置唤醒预算、主持人标志即停止、配置下界/零关闭/默认值。
- 唤醒是新的模型可见输入：走既有合成 `user/message` 路径（`wakeChatroomModerator`），消息 metadata 带 `chatroomSupervisorWake` 标记，活动追踪因此跳过它。
- 覆盖面：机制 A 让所有 continuable-subagent 消费方受益——任何群、项目、前端；聊天室只是第一个被完整取证的患者。机制 B 落地时只覆盖 hub↔管家关系，同日的提问身份路由工作已把监督网扩展到未决串行提问（见[提问身份路由](2026-09-06-chatroom-ask-identity-routing.zh.md)）：角色↔助手等待由其武装 gather 自带超时负责，通用 subtask 父级有用户可见面板且无持久任务状态，用户停驻的 ask 是有意等待。管家确已收工而主持人仍在 discussing 中静默的房间同样读作 stalled——叫醒主持人推进房间正是设计意图。
- 管家长任务期间，监督网每期限的催办代价是一个主持人回合 + 一个管家回合；管家的状态答复重置时钟。
- 部署：bridge 重建 + `/reload`；之后冻结的事故房间在一个扫描周期内收到首条监督唤醒，journal 的 `chatroom: supervisor woke stalled moderator` 行标记每次介入。
