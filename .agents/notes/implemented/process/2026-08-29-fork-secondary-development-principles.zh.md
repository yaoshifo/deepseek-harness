# Agent Note: Fork 二次开发原则

Status: implemented

English | [中文](2026-08-29-fork-secondary-development-principles.md)

## Problem

fork 在 `dev` 上分批吸收上游更新，同时承载自己的特性，但没有任何成文规则约定 fork 改动应该落在哪里、一次吸收的批次允许长到多大、以及哪些基础设施允许 fork 偏离。2026-08-29 对上游 1079 个提交（`dsh-v0.1.2-alpha.1` 范围）的吸收把这份缺失政策的代价摆到了明面上。解冲突本身是可控的；其后的验证收敛环不是：

- 165 处冲突中约 40% 是双语 README 配对，fork 的载荷只是特性散文，而翻译配对门禁让每一处都以两种语言计价——它把 merge 提交拦下了两次。
- 每个嫁接在上游拥有缝上的 fork 特性（审批常驻授权、session origin、委派 `cwd`、lsp 符号查找）都要在缝的新位置重新嫁接；而 fork 本地包（`feishu-bridge`，270 个文件）零冲突通过。
- 一次 fork 工具链偏离——[原生 tsconfig-paths 解析](2026-08-27-vite-native-tsconfig-paths.zh.md)——让上游新增的 face-split 包经由 package `exports` 加载了第二份模块单例，产生 33 个假测试失败，最终只靠与纯净 `upstream/master` worktree 对照才完成归因。
- 吸收中途的一次 `pnpm add` 静默丢掉了包级依赖，又制造了三个假失败。

## Decision

五条原则约束 `dev` 上的二次开发：

1. **同步节奏封顶。** 上游重构活跃期（目录退役、包拆分、启动器变更）至多每 2–3 天吸收一次，平静期至多每周一次；待吸收批次超过约 800 个提交即视为立即同步的信号。收敛成本随批次规模超线性增长，因为更大的批次包含更多 fork 改动必须跟随的缝移动。
2. **落点分层。** fork 改动优先落在 fork 本地包。必须改上游拥有的缝时，把改动收敛到最少的文件数，特性稳定后向上游提 PR：下一次吸收时合并上游等价实现，比每次吸收都重新嫁接一份 fork 差异便宜。
3. **不编辑上游文档正文。** fork 特性写在 fork 拥有的文件里——fork 本地包的 README 或独立的 fork 章节——而不是改上游拥有包的双语 README 配对。配对门禁在此后的每次合并都会为这类编辑重新计价。
4. **不 fork 工具链。** 构建与测试基础设施与上游逐字一致。偏离需要一个它修复的具体故障加上一条记录在案的回退触发条件；消警告这类装饰性动机不算。原生解析偏离就是参照失败案例：它的逐导入方向上发现机制看不见上游后来新增的 face-split 包。
5. **吸收操作纪律。** 吸收中途绝不运行 `pnpm add` 而事后不做完整 `CI=true pnpm install`；不熟悉的测试失败先对照纯净 `upstream/master` worktree 归因，再诊断合并；每解完一批冲突就重跑 `typecheck`，不攒到最后一次性跑。

[sync skill](../../../.agents/skills/dsh-sync-upstream/SKILL.md) 承载操作流程与坑；本 note 持有长期原则。

## Alternatives considered

- **只控节奏。** 每天同步而不配合其余原则能缩小批次，但每次吸收仍要照付缝嫁接与工具链漂移的税。
- **把所有 fork 形状的东西都上游化。** 上游评审带来时延与拒绝风险，且纯 fork 产品决策（飞书桥）没有上游归宿。原则 2 和 3 让这道分界保持 deliberate，而非最大化上游化。
- **基于 rebase 的维护。** 拒绝：共享已推送的 `dev` 上 rebase 需要 force-push 公共分支，而这正是合并式同步流程要保护的东西。

## Consequences

- fork 改动向 fork 本地包集中，后续吸收的冲突面应相应收缩到 fork 本地缝的集合。
- 提交上游的特性带时延且可能以修订后的形态落地；落地前 fork 承载差异，落地后下一次吸收仍需一次语义合并。
- fork 文档以 fork 拥有的文件增长，而非上游配对编辑，其可发现性依赖 `AGENTS.md` 里的 fork 政策指针。
- 节奏封顶的代价是更频繁、更小的同步会话；每次都要重跑 install、生成器与聚焦测试套件。
