# Agent Note: Followups card submissions dispatch readable selection messages

Status: implemented

English | [中文](2026-09-07-feishu-bridge-followups-selection-message.zh.md)

## Problem

The closing-card followups conversion dispatched the card submission as the raw wire payload `fw:{i1},{i2}` (note after a NUL separator) flagged `isFollowupAction`. The engine routes that flag to a fresh turn and hands the message text to the agent verbatim, so the model's next prompt was literally "fw:1" — an internal transport code the system prompt never describes, while the agent-conventions prompt promises the selection arrives as a「[后续处理]」new message. Every followups submission therefore cost the model a confused clarification round (observed 2026-09-07 oc_0481474: one ask_user_question round plus ~880 reasoning tokens spent guessing what "fw:1" meant; the user rescued it through the clarification card). The README, the introducing commit's message, and the engine tests' mocked content all described the readable self-contained message; only the implementation was missing, and the `followups_selection` message-table entry defined for its headline was referenced nowhere.

## Decision

The Feishu platform's `fw_multi:` intake composes the dispatched text at the submission point, where the send-time meta (question, options, descriptions) is already in hand for the card freeze:

- `followupsSelectionMessage` (engine/ask.ts) builds the message: the `FollowupsSelection` headline, the question, one `✅/◻️ **label**` + description mark per option, and the `✍️` note line. The mark construction is shared with the settled freeze card (`settledOptionMarks`), so the dispatched text and the user-facing frozen card cannot drift apart.
- Without cached meta (a newer askq card owning the cache key, or a registration past its persistence window or lost to a crash mid-send — registrations otherwise survive restarts; [followups meta persistence](../bug-fix/2026-09-09-feishu-bridge-followups-meta-persistence.md)) the dispatch is a localized `followups_stale` notice naming the checked indices, the question hint from the callback value when present, and the note — the raw `fw:` payload never reaches the model on any path.
- `isFollowupAction` routing semantics are unchanged; only the dispatched text changed.

## Alternatives considered

**Engine-side expansion at the routeAskResponse fall-through.** Rejected as the placement: by the time the engine sees the message, the interactive state's `pendingFollowups` is consumed and the option labels live only in the platform's meta cache — the submission point is where the labels and the freeze already are, and one composition site keeps the dispatch and the freeze symmetric.

## Consequences

The agent's next prompt after a followups submission is a self-contained selection report (headline, question, checked and skipped labels with their `path:line` descriptions, note), so the model acts on the checked items directly instead of guessing at indices. A stale card's submission degrades to a confirm-with-user notice instead of an uninterpretable payload. Pinned by `tests/feishu/card-action.spec.ts` (readable dispatch with labels and note, note-only submit, stale notice with note) and `tests/engine/followups.spec.ts` (routing mocks generated by `followupsSelectionMessage`).
