# Agent Note: 计划卡影子推敲群

Status: implemented

[English](2026-09-17-feishu-bridge-plan-shadow.md) | 中文

## 问题

计划卡会挂起它所在的回合直到用户作答，而这段挂起窗口正是征询第二意见最便宜的时机：卡片上的备注输入本来就会随裁决进入 `exit_plan_mode` 的拒绝路径，所以用户再推一次（「还有没有更好的、更鲁棒的、更优雅的方案？」）有可能拿到更好的计划。手动这么做要花掉手上这张计划——同一个会话会重新规划，眼前这张卡没了——而且这一步没人能可靠地坚持做。

把它自动化需要第二个由同一份会话记录播种的对话，这部分桥本来就能做（`/fk`），但桥不拥有另外两件事：

- 计划卡发出后没有挂点。`feishuBridge/ask-parked` 只对问题类询问触发；计划路径止于 `deliverCards`，没有任何东西可供监听。
- 两个这样的对话无法互相结算。用户批准哪一张，另一张就必须作废，而两者之间没有任何关联。

## 决策

`engine/plan-shadow.ts` 拥有这个功能；`Engine.askUser` 的 plan-review 分支是它唯一的入口。

**发起。** 就在计划卡落地、询问挂起之后——`deliverCards` 竞速之后、决策等待之前——`launchPlanShadow` 以 fire-and-forget 运行，因此建群绝不会卡在挂起的卡片和用户的批准窗口之间。影子群是一个 `/fk` 形状的孩子：`spawnGroupCommon` 配 `forkSentinelID = __fork__<nativeID>`、`modeArg: 'plan'`，首条注入消息就是那段推敲话术。子群是全新群，沿用原群的工作目录、provider 路由与成员；不建 worktree，因为计划模式的会话不碰工作树。

**护栏**（全在 `canLaunch`，全部静默跳过）：项目开关、计划有正文、平台能建群、可 fork 的原生会话 id（已启动，既非 `__fork__` 也非 `__forkat__`）、发起人既非空也不是 cron 的合成发送者——影子群唯一的成员就是这个人，围绕 `cron` 建出来的群没人打得开、更别说批准——自身不是影子群，且尚未发起过。「一个会话至多一个影子群」记在 `Session.featureState.planShadow` 上：原会话记 `shadowSessionKey`，影子记 `shadowOf`。该区段有意不带 codec——它会持久化进会话快照，但没有任何 codec 会在会话重置时搬走它，因此 `/new` 重新武装这个功能是正当的。

**命名与告知。** 群名为 `<原群名> · 推敲`，经 `truncateGroupName` 截断。原群名取会话标签（除非它还停在通用的 `defaultSessionName` 占位值上），否则取从该群消息里记下的名字；两者都没有时沿用 `/fork` 的占位名，由既有的首条消息改名接管。有意不走 `sessionDisplayName`——它剩下的兜底（占位值，再到裸会话 key）服务于 `/list` 与 `/status` 的行，而两者都不适合出现在本功能新建的聊天列表条目里——也有意不做无条件占位名，因为那样改名的素材会变成这段推敲话术。`SpawnCommonOpts.parentNotice` 把说明行带上原群已有的跳转卡；说明必须同时走两条发送路径（卡片句柄那条与 `sendAsCardWithButtons` 降级那条），因为只挂在其中一条上，在不支持卡片句柄的平台上会被静默丢掉。`/spawn` 与 `/fork` 不传说明，保持它们只有按钮的卡片。

**双向结算。** 两个调用各自守门，而一个会话绝不会既是影子又是影子的发起者：

- 批准原计划调用 `abortPlanShadow`：`markSpawnedChatDone` → `setChatPhase('done')` → `stopInteractiveSession` → 在影子群里贴作废通知。终态先于停机提交，与 `/done` 的顺序一致，使迟到的重绘能看到置灰标记。
- 批准影子的计划调用 `invalidateOriginPlan`，它停掉原群挂起的回合而不只是取消询问：只取消 `exit_plan_mode` 会让原群 agent 重新规划并挂出第二张竞争的卡片。原群收到一条带跳转按钮的通知。

`spawnGroupCommon` 现在返回合成的子消息（调用方需要子会话 key 来关联这一对），并接受可选的父群说明。所有失败路径未变，仍在原群自报，因此影子路径不会多出第二条失败提示。

**配置。** `projects[].planShadow.enabled`（默认 true）与 `planShadow.prompt`（默认：`plan-shadow.ts` 出厂的那段话术，被一条用例逐字钉住）。话术就是用户要的部署旋钮：改影子被问什么，不需要重新构建。

## 考虑过的替代方案

- **在同一个会话里把推敲文本自动当成计划反馈提交。** 最便宜，也最接近用户手动做的事，但它花掉了原群那张卡：整件事的要点就是推敲在跑的同时原计划仍然可批准。
- **每张计划卡都开一个影子群。** 用户否决：飞书删不掉群，多一张卡就多一个永久群。会话的第一张卡也是第二意见最有机会改变结果的时点。
- **在同一会话后续卡片间复用同一个影子群。** 避免群堆积，但要么群里得中途重新武装，要么它的历史会混进对不同计划的推敲；「只第一张卡」用同样的代价换来边界，且不需要重新武装的状态。
- **用 `sessionDisplayName` 的兜底值命名群。** 最省事，但在从未记下名字的群里，它会把通用的 `default` 标签或裸会话 key 放进聊天列表——只有线上数据能看出这件事（817 个活跃会话里 754 个有真名，其余没有），所以这个分支被一条用例钉住，而不是留给顺利路径。
- **即使推敲认为没有改进也强制出计划卡。** 用户裁定交给 agent 决定：强制的「改进」会招来为改而改。影子没有更好的方案时就以文字作答。
- **把 `feishuBridge/ask-parked` 扩展到 plan-review，而不是直接调用本模块。** 该事件现有消费者会武装研究群的询问超时；新增一个派发方会把那条策略悄悄延伸到计划类询问。从询问自己的分支直接调用（`plan-render` 已经用的形状）只改计划路径。
- **把影子身份记在建群注册表（`SpawnedChatMeta`）里。** 阻止套娃的护栏读的是发起询问那个会话自己的记录，而引擎要看到它就得伸手进平台自己的存储；`Session.featureState` 是会话作用域的家，也正是为此准备的口袋。
- **删除或关闭作废的影子群。** 飞书没有任何解散群的 API：置灰加通知就是全部可用的生命周期。

## 后果

- **成本。** 每个会话的第一张计划卡换来多一个群、一次完整的会话记录 fork、一轮计划模式回合——外加一个用户没要过的飞书群，由原群的跳转卡解释其来由。
- **群会积累。** 作废的影子群留在聊天列表中，只是置灰。「每会话第一张卡」给它设了上界，`/new` 会重置计数，完全不想要的用户把 `planShadow.enabled` 设为 false。
- **竞态。** 如果影子群还在创建时原计划就被批准，中止会作用在一个已经建出来的群上：它会被置灰并作废，但它确实存在。这是有意接受而非串行化——为了建群去堵批准窗口更糟。
- **无人值守的计划永不开群。** cron 的合成发送者会被拒绝；其他机器唤醒的回合仍属于某个真实用户的聊天，那里存在能批准的人。
- **验证。** `packages/acp/feishu-bridge/tests/engine/engine-plan-shadow.spec.ts` 对着 stub spawner 驱动 `Engine.askUser`：子会话的 fork 哨兵与计划模式、群名与两条通知、每会话一次、防套娃与 cron 两条护栏、开关、双向结算（含停机顺序与被冻结的原群卡片），以及逐字的推敲话术。`tests/assembly-config.spec.ts` 钉住配置转发与默认值。一次突变检验（摘掉结算接线）恰好让两个结算用例变红。
- **部署。** 重新构建桥 + `/reload`；功能默认开启，采纳它不需要改任何配置。
