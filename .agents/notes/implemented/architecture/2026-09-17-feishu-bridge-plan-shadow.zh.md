# Agent Note: 计划卡影子推敲群

Status: implemented

[English](2026-09-17-feishu-bridge-plan-shadow.md) | 中文

## 问题

计划卡会挂起它所在的回合直到用户作答，而这段挂起窗口正是征询第二意见最便宜的时机：卡片上的备注输入本来就会随裁决进入 `exit_plan_mode` 的拒绝路径，所以用户再推一次（「还有没有更好的、更鲁棒的、更优雅的方案？」）有可能拿到更好的计划。手动这么做要花掉手上这张计划——同一个会话会重新规划，眼前这张卡没了——而且这一步没人能可靠地坚持做。

把它自动化需要第二个由同一份会话记录播种的对话，这部分桥本来就能做（`/fk`），但桥不拥有另外两件事：

- 计划卡发出后没有挂点。`feishuBridge/ask-parked` 只对问题类询问触发；计划路径止于 `deliverCards`，没有任何东西可供监听。
- 两个这样的对话无法互相结算。用户批准哪一张，另一张就必须作废，而两者之间没有任何关联。

把两者关联起来还不够：批准只是「这张计划卡办完了」的一种方式，而且是较少见的那种。用户打字作答、点拒绝，或在推敲群里回答一个提问，都已经做了决定，而对侧还在等——推敲继续白白烧完一个没人等的方案，或者原群那张卡一直停着等一个已经不再决定任何事的结果，而清理对侧要靠手动 `/done`，那还会顺手带走对侧的子群。

## 决策

`engine/plan-shadow.ts` 拥有这个功能，入口有三个：`Engine.askUser` 的 plan-review 分支（挂着的卡被批准了）、`Engine.handleInbound`——平台投递的每一条人类动作都经过的入站口（`handleMessage` 本身仍是合成注入共用的路径），以及 `Engine.handleResultEvent` 的收尾处——没有停过计划卡的推敲回合在那里收尾自己的群。

**发起。** 就在计划卡落地、询问挂起之后——`deliverCards` 竞速之后、决策等待之前——`launchPlanShadow` 以 fire-and-forget 运行，因此建群绝不会卡在挂起的卡片和用户的批准窗口之间。影子群是一个 `/fk` 形状的孩子：`spawnGroupCommon` 配 `forkSentinelID = __fork__<nativeID>`、`modeArg: 'plan'`，首条注入消息就是那段推敲话术。子群是全新群，沿用原群的工作目录、provider 路由与成员；不建 worktree，因为计划模式的会话不碰工作树。

**护栏**（全在 `launchableSession`，它把原会话交给发起路径，每一次跳过都是静默返回 `undefined`）：项目开关、计划有正文、平台能建群、会话记录存在、可 fork 的原生会话 id（已启动，既非 `__fork__` 也非 `__forkat__`）、发起人既非空也不是 cron 的合成发送者——影子群唯一的成员就是这个人，围绕 `cron` 建出来的群没人打得开、更别说批准——自身不是影子群，且尚未发起过。「一个会话至多一个影子群」记在 `Session.featureState.planShadow` 上：原会话记 `shadowSessionKey`，影子记 `shadowOf`。该区段有意不带 codec——它会持久化进会话快照，但没有任何 codec 会在会话重置时搬走它，因此 `/new` 重新武装这个功能是正当的。

**命名与告知。** 群名为 `<原群名> · 推敲`，经 `truncateGroupName` 截断。原群名取会话标签（除非它还停在通用的 `defaultSessionName` 占位值上），否则取从该群消息里记下的名字；两者都没有时沿用 `/fork` 的占位名，由既有的首条消息改名接管。有意不走 `sessionDisplayName`——它剩下的兜底（占位值，再到裸会话 key）服务于 `/list` 与 `/status` 的行，而两者都不适合出现在本功能新建的聊天列表条目里——也有意不做无条件占位名，因为那样改名的素材会变成这段推敲话术。`SpawnCommonOpts.parentNotice` 把说明行带上原群已有的跳转卡；说明必须同时走两条发送路径（卡片句柄那条与 `sendAsCardWithButtons` 降级那条），因为只挂在其中一条上，在不支持卡片句柄的平台上会被静默丢掉。推敲群自身收不到任何说明消息：群里的人靠群名后缀与那张跳转卡辨识这个群。`/spawn` 与 `/fork` 不传说明，保持它们只有按钮的卡片。影子群还继承原群的头像身份：发起时把原群 session key 作为 `GroupSpawnOptions.avatarFrom` 传下去，平台据此用原群的记录播种新群记录——它渲染好的图标名加一份各相位图片 key 的拷贝——并让建群调用携带原群 `discussing` 那张 key，新群因此出生就戴着这张脸，不会先闪一下 bot 头像。此后影子群自己的相位照常换色（讨论中黄、计划待批蓝、已批准绿、已关闭灰），原群没渲染过的相位从拷贝来的图标名懒渲染，两群因此读起来是孪生群。这份身份是稳定的：给 spawn 群发图标的正是命名流程，而以 `<原群名> · 推敲` 出生的影子群永不进入它——`isSpawnPlaceholderName` 拒绝首条消息改名，因此没有任何后续步骤会重盖出生时那张脸。图片 key 都是本应用自己上传的，两群复用无需重新上传，相位表是拷贝而非共享引用；`/spawn` 与 `/fork` 保持各自的命名路径——它们的图标本就来自那里。

**双向结算。** `settlePlanShadowPeer` 是唯一入口，调用时带一个说明「发生了什么」的 trigger——被批准是 `approved`，其余用户动作都是 `input`——而动作所在会话自己的记录就说明了它是这一对的哪一侧，因此一次调用覆盖两个方向，文案从一张 2×2 表里取。`claimPeer` 就是那条「一对只结算一次」的护栏：配对区段已带 `settled` 时它拒绝放行，并在返回前把 `settled` 同时提交到双方记录上，因此同一个 tick 里两个结算不可能都通过。`Engine.askUser` 的批准分支以 `approved` 调用它；平台入站口以 `input` 调用它。

- **什么算「动手」**（`isUserAction`）：文字、附件，以及卡片按钮（权限裁决、追问卡作答、追问续做卡提交、命令快捷按钮）都会结算对侧。杂务不算——以 `/` 开头的消息，以及查询类按钮（`/list` 翻页、`/status` 刷新背后的 `act:`/`nav:` 族）是你在查一个群的状态，不是在动这一对。合成注入根本到不了这条路径：spawn 群的首条消息与每一次机器唤醒都经 `receiveMessage` 直接进入 `handleMessage`，绕过平台入站口。落在本群自己挂着的 plan-review 询问上的「批准」裁决交给那张卡自己的结算（`isPlanCardApproval`）——它的文案点名「批准」，并且同样覆盖那些从未以点击形式到达的裁决——因此每个动作只有一条路径结算。
- **关对侧**走同一个 `closeChat`——`markSpawnedChatDone` → `setChatPhase('done')` → `stopInteractiveSession`，终态先于停机提交，使迟到的重绘看到置灰标记。影子那一侧还会放过已带终态标记的群；原群那一侧保留两条边界：只有活着的 spawn 群会被置灰——主群、私聊没有头像轴，收到的是不宣称关群的提示——而已带已结束标记的群（上一次结算关掉的，可能又已被唤醒）只是卡片自己静默作废。停掉的是挂起的回合而不只是取消询问：只取消 `exit_plan_mode` 会让原群 agent 重新规划并挂出第二张竞争的卡片；而且没有任何「忙」的豁免——对侧挂着的任意种类询问、或正在跑的无关回合，都随会话一起停：在一侧动手就是全赢。与批准路径一样，关群不走 `/done` 的 `cmdDone`/`cleanupOneChat`，对侧的子任务群与 worktree 一概不动，`feishuBridge/pre-done` 也不触发。通知落在对侧：推敲群收到一张纯文本卡，原群收到的卡片带跳进推敲群的按钮。
- **建群竞态。** 建群要花一点时间，而原群那张卡可能正好在这个窗口里被作答——那时关联还没写下，所以那次结算找不到对侧可关。`runLaunch` 因此在写完关联后重读原群的挂起状态，把「决定之后才出生」的群在到场时即结算。这个窗口里的一条普通发言与「没有任何发言」无法区分（它不改变任何发起路径读得到的状态），而那时原群仍停在它的卡上，所以新生儿被保留。

**推敲无产出即收尾。** 推敲群的一轮走到终点、而没有停下等一张计划卡时，这一对就没有可等的裁决了，于是 `closePlanShadowOnTurnEnd`——由 `Engine.handleResultEvent` 的收尾处调用，位置在该回合的终态卡与基线重涂之后，且只对既未报错、也没有留下排队消息的前台回合——按结算用的同一个 `closeChat` 关掉推敲群：提交终态标记、头像置灰、结束会话。plan-review 询问一 park 就挂住回合，所以抛出过计划的回合根本到不了那个收尾点：能走到那里，本身就意味着没有停过计划卡。规则绝不触碰原群，那张卡照旧可批准；它也不写 `settled` 标记，因此用户把已收尾的群唤醒、从它那里拿到新计划并批准时，这一对仍会被结算、原群仍会被关掉。已被结算的一对（影子群的计划赢了，或原群动了手）不受影响；已带终态标记的群同样不受影响——每个群至多被这条规则收尾一次。

`spawnGroupCommon` 现在返回合成的子消息（调用方需要子会话 key 来关联这一对），并接受可选的父群说明。所有失败路径未变，仍在原群自报，因此影子路径不会多出第二条失败提示。

**配置。** `projects[].planShadow.enabled`（默认 true）与 `planShadow.prompt`（默认：`plan-shadow.ts` 出厂的那段话术，被一条用例逐字钉住）。话术就是用户要的部署旋钮：改影子被问什么，不需要重新构建。

## 考虑过的替代方案

- **在同一个会话里把推敲文本自动当成计划反馈提交。** 最便宜，也最接近用户手动做的事，但它花掉了原群那张卡：整件事的要点就是推敲在跑的同时原计划仍然可批准。
- **每张计划卡都开一个影子群。** 用户否决：飞书删不掉群，多一张卡就多一个永久群。会话的第一张卡也是第二意见最有机会改变结果的时点。
- **在同一会话后续卡片间复用同一个影子群。** 避免群堆积，但要么群里得中途重新武装，要么它的历史会混进对不同计划的推敲；「只第一张卡」用同样的代价换来边界，且不需要重新武装的状态。
- **用 `sessionDisplayName` 的兜底值命名群。** 最省事，但在从未记下名字的群里，它会把通用的 `default` 标签或裸会话 key 放进聊天列表——只有线上数据能看出这件事（817 个活跃会话里 754 个有真名，其余没有），所以这个分支被一条用例钉住，而不是留给顺利路径。
- **即使推敲认为没有改进也强制出计划卡。** 用户裁定交给 agent 决定：强制的「改进」会招来为改而改。影子没有更好的方案时就以文字作答——这一轮的终点会顺手收尾它自己的群，而不是把这次推敲留着开着。
- **把 `feishuBridge/ask-parked` 扩展到 plan-review，而不是直接调用本模块。** 该事件现有消费者会武装研究群的询问超时；新增一个派发方会把那条策略悄悄延伸到计划类询问。从询问自己的分支直接调用（`plan-render` 已经用的形状）只改计划路径。
- **把影子身份记在建群注册表（`SpawnedChatMeta`）里。** 阻止套娃的护栏读的是发起询问那个会话自己的记录，而引擎要看到它就得伸手进平台自己的存储；`Session.featureState` 是会话作用域的家，也正是为此准备的口袋。
- **把作废的影子群删掉，而不是置灰。** 飞书没有任何解散群的 API，所以置灰——被对侧结算时配通知，推敲自收尾时不配——就是全部可用的生命周期；真要解散得有飞书并未提供的接口。
- **用 `/done` 自己的调用路径（`cmdDone`/`cleanupOneChat`）关原群。** 收尾顺序与 `closeChat` 复制的那套相同，但 `cmdDone` 还会走遍原群的子任务群、排空其原生子任务、处置它的 worktree（含交互式 Keep/Remove 卡），并触发别的插件在其上清理状态的 `feishuBridge/pre-done`。被影子批准取代的计划与这些资源毫无关系，所以关群止于原群本地。
- **整个规则改由对侧建群注册表里的已结束标记驱动，而不引入配对数级的一次性标记。** 那个标记是平台自己的真值，单靠它就能覆盖被跟踪的对侧；但平台不跟踪的对侧（主群、私聊）永远不带它，于是那边此后每一条消息都会再停它一次、再播报一次；一次性标记还让两条结算触发互不竞态（它同步提交，早于任何 await），而事后回看标记做不到。
- **只把批准当作结算，其余动作一概不管。** 本次改动之前的线上行为；它把手动 `/done` 留给用户，并让一侧为一个已经做出的决定继续烧活，这正是本次引入入站入口与一次性标记要解决的问题。
- **在建群之前先占位（让 `shadowSessionKey` 指向一个还没建出来的群），使建群期间的动作也能作废它。** 这能把「普通发言」那个窗口也覆盖掉，但占位是持久状态：写在写入与建群之间崩一次，就留下一个再也发起不了推敲的群，而发起护栏读的正是同一个键。改成建群后重读挂起状态，窗口有界且不留下任何半状态。

## 后果

- **成本。** 每个会话的第一张计划卡换来多一个群、一次完整的会话记录 fork、一轮计划模式回合——外加一个用户没要过的飞书群，由原群的跳转卡解释其来由。
- **群会积累，收尾与否都一样。** 推敲无产出时群会在它那一轮结束时置灰，但没有任何群会离开聊天列表；而推出更好方案的推敲群则活着跑自己的计划。「每会话第一张卡」给它设了上界，`/new` 会重置计数，完全不想要的用户把 `planShadow.enabled` 设为 false。
- **只有走完的回合才收尾。** 报错中断的回合、还握着排队消息的回合、后台任务回合都让群保持开着；那些根本到不了 result 路径的终局同样如此——用户停止、stall 强杀、硬上限、agent 错误事件、无文本的 channel 关闭：群随后等用户处理，用户可以在群里重试，或跑一条 `/done`。
- **竞态。** 在原群卡片正被作答期间出生的群，在它存在的那一刻即被结算——置灰、停会话、被告知——而不是留下一个推敲已被决定方案的群；批准窗口依然不等建群。接受这个有界的窗口，而不是串行化。
- **无人值守的计划永不开群。** cron 的合成发送者会被拒绝；其他机器唤醒的回合仍属于某个真实用户的聊天，那里存在能批准的人。
- **被关掉的原群再发一条消息就醒。** 结算结束的是原群的会话而非它那个群：用户发一条消息，群照常继续——与 `/done` 的置灰同一条复活路径。
- **平台不跟踪的原群只作废、不关。** 主群或私聊没有头像轴，结算止于卡片、挂起的回合与通知；只有活着的 spawn 群才会被置灰。
- **在配对任一侧动手都会结束另一侧正在做的事。** 对侧有无关回合在跑、或挂着别的种类的询问，都不构成豁免：关群会停掉会话，那件工作也在内。用户选了这条，而不是更安静的关法——留着半活的配对正是这条规则要消除的东西。
- **一对只结算一次。** 首次结算之后，任一侧都不会再关另一侧、也不会重复播报；用户把已关的群唤醒同样如此（下一条消息会让头像回到基线色，但标记还在），平台无法置灰的对侧亦如此——否则那边此后每一条消息都会再停它一次、再解释一次。
- **触发面是规则而非启发式。** 除纯查询以外的斜杠命令（含 `/done`）以及任何推动对话的卡片按钮都算动手；翻页与刷新按钮不算。因此在推敲群发一条 `/done`，也会作废并关掉原群。
- **头像继承有下限、也不追溯。** 原群没有桥自绘图标时（主群、私聊、或从未拿到过图标的群），影子群在每个相位都维持 bot 头像，与从前一致；且只有改动之后新建的影子群才继承，已存在的影子群停留在它当前戴着的头像上。
