# Agent Note: 派生群继承原群的路由

Status: implemented

[English](2026-09-16-feishu-bridge-child-group-route-inheritance.md) | 中文
## 问题

`/provider` 按群固定模型路由：覆盖记录持久化在项目状态中，重启后仍生效，且从不移动项目默认路由。而派生群只从 `agent.spawnProvider` 取路由，于是被切到另一条路由的群仍然会派生固定 spawn 默认路由的子群——若未配置该项，则用项目默认路由。因此，一个复制了完整对话上下文的 fork，实际会在与原对话不同的模型上运行该上下文，子群卡片上也没有任何提示。

## 决策

`Engine.seedSpawnProvider(childKey, parentKey)` 解析子群路由：当原群的有效路由与项目默认路由不同时取原群那条，否则取配置的 `agent.spawnProvider`。`/spawn` 与 `/fork` 都经 `spawnGroupCommon` 传入原群的 session key，因此两条命令的继承行为一致。写入的是一条普通按群覆盖记录：经 provider 保存钩子持久化，在子群内可切换、可清除，且清除后回落到项目默认路由而非继承来的路由。原群没有覆盖记录——或其路由已从 `config.providers` 中删除——时，经 switcher 既有的回落逻辑读作「处于项目默认路由」，于是仍适用 spawn 默认路由。

无人值守的子任务群、聊天室角色群与监控子群保持 spawn 默认路由：`spawnSubtask` 有意不传原群 key，因为这些子群是没人按群盯着的执行者。

## 考虑过的替代方案

**读取原群的原始覆盖记录，只要存在就继承。** 这需要在 `ProviderSwitcher` 接缝上新增读取方法，而且一条失效记录（写入后其路由已从配置删除）会试图继承一个子群无法解析的名字。改比较有效路由，则恰好在这类情形上复用 switcher 既有的回落逻辑。可见差异很窄：把原群显式固定到本就等于项目默认的那条路由，会被读作「从未切换」。

**在每条派生路径上都继承。** 子任务群、角色群与监控子群是无人值守的执行者；把它们的路由耦合到原群碰巧切到的那条，会在无人看管该群的情况下改变成本与能力。

**保留现有行为并把它写进文档。** 按群切换是用户对该群工作的意图；一个复制了上下文却不复制模型的 fork 会让这一意图静默失效——没有任何卡片展示子群的路由。

## 后果

`agent.spawnProvider` 现在的含义是「原群处于项目默认路由时，其派生群所用的路由」：若某个部署把群切走、又指望这些群派生固定成本的子群，则该群不再享有这一固定。变更前已建的群保留其持久化覆盖记录，运行中的 daemon 也要等下一次 reload 才带上这次变更。引擎字段 JSDoc、配置 schema JSDoc 与装配注释都记录了收窄后的含义。归属 spec 覆盖了：两条命令上的继承、持久化的写入、未配置 spawn 默认路由的情形、原群固定为项目默认路由的边界，以及原群解析不出任何路由的情形；子任务 spec 则固定其未受影响的 spawn 默认行为。
