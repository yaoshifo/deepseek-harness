# Agent Note: feishu-bridge de-baggage batch 2 — ask delegate with native approval and question structures

Status: implemented

English | [中文](2026-08-24-feishu-bridge-ask-delegate.zh.md)

## Problem

The bridge's approval and question loop was still the Go bridge-protocol shape after the dsh cutover, and B1 ([approval seam](../feature/2026-07-06-approval-seam.md)) had already grown the native primitives it should have been using:

- The adapter's `approval/request` answerer compressed every native ask into a synthetic `permission_request` event on the session's EventChannel; the engine's event loop owned a `PendingPermission` state machine; the user's verdict travelled back through `AgentSession.respondPermission` into one of two adapter wait tables (`pendingPermissions`, `pendingQuestionAnswers`).
- One ask with several questions rendered one card per question, advancing a `currentQuestion` cursor; free text was stuffed into `selected` as a single string, so the native `custom` channel never carried free-text answers.
- `perm:allow_all` set a Go-era `state.approveAll` flag instead of the native `allowed-always` standing grant; a deny note was wrapped in a Claude-Code-shaped rejection preamble and steered as a separate user message, while the native tools executor already folds `ApprovalAnswer.note` into the rejection text.
- The permission card showed `ApprovalRequest.reason` masquerading as the tool-input preview; `toolInput` (B1) went unused.
- The `askq:{q}:{i1},{i2}` button-value protocol was parsed independently by the engine's answer resolver and the Feishu platform's callback branch.

## Decision

One typed delegate method replaces the synthetic event, the state machine, and both wait tables; answers travel in the native structures.

- **`Engine.askUser(sessionKey, request, signal?)`** is the only ask surface. `AskRequest` is a closed union — `{ kind: 'permission', toolName, preview }`, `{ kind: 'plan-review', heading, plan }`, `{ kind: 'questions', questions }` — and `AskDecision` returns the native outcome vocabulary (`allowed-once`, `allowed-always`, `rejected`, `cancelled`, plus an optional note) or per-question answers with the selected/custom split. The adapter's approval answerer and `userQuestions` provider delegate to it through the `AskDelegate` interface that `index.ts` injects after engine construction, keeping the engine→agent dependency one-directional. Sessions without an interactive state (relay, background shells) auto-allow permission asks and return empty answers — the Go relay auto-approve semantics without the relay loop needing to know about asks at all.
- **The event loop no longer sees asks.** The `permission_request` `EventKind`, the loop's 256-line case, `PendingPermission`, `approveAll`, `permissionPending` (write-only), `PermissionResult`, and `AgentSession.respondPermission` are gone. The turn surfaces the case touched (text accumulation, segment boundaries, preview, progress writer, timing, plan tracking) moved onto `InteractiveState`; the loop re-reads them at every select resolution, so the delegate's pre-card flush/detach and post-decision surface restart land exactly where the old in-loop blocks ran. The idle timer is not armed while an ask is parked — a user deciding is not a stall.
- **One card carries every question.** `buildAskQuestionsCard` (engine/ask.ts) renders each question as list rows (`askq:{q}:{n}` buttons) or a checker form (`askq_multi:{q}`), and the Feishu callback response rebuilds the card from a send-time cache of the whole question set. `askqAnswered` shrinks from a boolean per card message to the answered-question set. Card-less platforms get every question in one plain-text message; the first unanswered question's options ride inline buttons; free text answers the first unanswered question. The answered-question rendering and the free-text routing evolved into the live form with per-question text channels ([live-form note](../feature/2026-08-31-feishu-bridge-ask-live-form-card.md)): answered-but-open questions keep their controls and show their current answer instead of freezing, chat text can address a question by an `N:` prefix, and card-input text rides the wire after a NUL separator.
- **`askq:` parsing converges to one pure function.** `parseAskqSelection` (engine/ask.ts) is the single parser for the wire format; the platform's callback branch and the engine's response routing both go through it. The legacy two-segment `askq:{n}` form is rejected — with all questions on one card it cannot name its question. `resolveAskAnswer` puts option selections in `selected` (labels) and free text in `custom`; card-input text riding a payload is the one case where both appear together ([live-form note](../feature/2026-08-31-feishu-bridge-ask-live-form-card.md)). The keyword tables survive only as the card-less fallback: the permission card dispatches its structured `perm:` payload verbatim, and `parsePermissionVerdict` consults `isAllowResponse`/`isDenyResponse`/`isApproveAllResponse` only for free text.
- **Verdicts map to native outcomes.** `perm:allow` → `allowed-once`; `perm:allow_all` → `allowed-always` (the B1 per-(agent, tool) standing grant decides later asks without dispatch); `perm:deny` plus card-input text → `{ outcome: 'rejected', note }`, which the tools executor folds into the rejection text — the bridge-side preamble builder and the ordinary-deny steer are gone because they would duplicate the note. An allow-side note rides the decision and the `approval/decided` audit pair. The permission card body shows `ApprovalRequest.toolInput` with `reason` as the fallback.
- **Plan review keeps the plan card.** The plan-review ask renders the plan markdown card (file-backed when the agent wrote a plan file this round, inline otherwise) awaited before the permission card, strips plan text already streamed from the reply source, and keeps the supplement steer on approval — plan-mode treats any `custom` as keep-planning feedback, so the note cannot ride the answer. Native plan mode owns mode transitions; the engine's `effectiveMode` mutation on approval is retired with the ExitPlanMode permission event it served. The chatroom pick window still auto-approves the moderator's plan review, now by resolving the delegate's promise directly.
- **The research-manual timeout is per ask, not per question.** One timer guards the whole card; on fire, `settlePendingAskDefaults` applies the first-option default to every unanswered question, keeps collected answers, and settles once. It no-ops when the user already resolved (the engine's settle clears the parked ask first), so a late fire cannot double-settle.

## Alternatives considered

- **Keep the event loop as the ask renderer via an internal channel signal.** Rejected: every variant of "the loop renders" is the synthetic-event pathway under another name; the loop cannot render while parked on `receive()`, and unparking it reintroduces the ordering coupling the delegate removes.
- **A shared ask-decision table keyed by request id.** Rejected: with the delegate returning a promise, the parked ask needs only what response routing reads (the request and collected answers); a second keyed table would restore the wait-table shape B2 deletes.
- **Freeze the whole ask card on the first question's answer.** Rejected: with every question on one card, freezing on the first callback would kill the other questions' buttons; the mixed frozen/interactive rebuild keeps the card usable while preserving the reviewed choice.
- **Steer ordinary-tool deny notes alongside the native fold.** Rejected: the note now reaches the model inside the folded rejection text, so steering would deliver it twice.

## Consequences

- Ask latency and card count change observably: one ask is one card regardless of question count, and `allowed-all` stops prompting for the same (agent, tool) pair for the agent's lifetime (B1 in-memory memo; a resumed session asks again). Covered by `tests/engine/ask.spec.ts` (protocol convergence), `tests/engine/engine-ask.spec.ts` (delegate lifecycle), the rewritten `engine-m3-permission|askq|plan` suites, `tests/agent-dsh/adapter.spec.ts` (answerer/provider delegation), and the Feishu `card-action` suite.
- The chatroom pick approval no longer blanket-approves the rest of the pick turn (`approveAll`): later tool asks in that turn surface as cards. The pick window reads role files (no approvals expected); real-machine smoke should confirm.
- While an ask is parked, events still on the channel (a still-running delegated child's tool activity) are processed by the live loop instead of queueing behind the old in-loop park; they land on the detached card's replacement surfaces. Real-machine smoke of a chatroom research round plus a concurrent child is the remaining verification point.
- Subagent children keep failing closed (`unavailable`) when they ask — lineage attribution is projection-only, unchanged.
