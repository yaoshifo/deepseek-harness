dsh 沙箱机制通俗解读

三个权限档位、两道共享图纸的围挡、一条审批升级通道。用装修工地的类比讲清楚 dsh 怎么限定 AI agent 动手能落到哪里。

一个生活类比先看全貌

想象你请了装修工人（AI agent）来家里干活。工人要刷墙、拧螺丝、搬东西——这些活你让他干，但你不想让他顺手翻卧室抽屉里的存折。

沙箱就是那个工地围挡：它不改变工人会干什么活，只限定他动手能落到哪里。工人手伸出围挡外，被挡住；围挡内，随便干。dsh 给 agent 配的文件沙箱，本质上就是这道围挡——agent 可以读代码、改文件、跑命令，但它的每一次文件写入都会被检查"你落到的工作区外的路径了吗"。

这里有一个关键特征容易被忽略：围挡只管"手能落到哪块地"，也就是文件效果（file effects）。工人能不能打电话、能不能看窗外——网络访问和进程可见性——不归这个围挡管。dsh 的沙箱是有意只覆盖文件写入这一层，不是一个通用安全沙箱。这是它的设计边界，不是缺陷。

核心特征

三档文件效果权限 × 两道共享同一张图纸的围挡 × 拒绝即事实加一次性审批升级 × 找不到围挡就宁可不跑。它管的是"文件能落到哪"，不是通用安全沙箱。

三档「施工许可」

整个沙箱只有三个权限档位，整个系统就认这三个词，没有中间地带。这个封闭词汇表叫 SandboxMode，所有围挡、所有策略、所有审批都围绕它转。

模式意思工人类比
read-only只能看不能改，连一个字都写不了。POSIX 上还会给 shell 留一个 /dev/null 当接收器，让 >/dev/null 能正常工作；Windows ACL 上不授予任何显式可写根目录。工人只能看图纸，不能动工具
workspace-write只能在指定工作区根目录下写入，外加平台临时区域（/tmp、os.tmpdir()）。这是大多数 agent 会话跑的默认档位。工人能在客厅干活、废料临时堆门口，但不能进卧室
danger-full-access不设围挡，整个家随便动。consumer 拿到这个模式时根本不调用 ctx.sandbox，直接 spawn 原始命令。工人信任度满级，全屋放行

前两档是"受约束的执行"——它们会到达沙箱提供方，被包一层 runner。第三档是"不受约束的执行"——它绕过沙箱，consumer 直接 spawn 原始 argv，不咨询 ctx.sandbox。

举例

一个会话的 cwd 是 /home/me/project，模式是 workspace-write。agent 写 /home/me/project/src/app.ts ——通过，在工作区内。agent 写 /etc/hosts ——被挡，工作区外。agent 写 /tmp/build.log ——通过，在平台临时区域内。

注意第三档

danger-full-access 不是"更宽的围挡"，而是"干脆不装围挡"。它是显式的无约束模式，不是更宽的沙箱 profile。你现在读这篇文档所在的会话就跑在这一档——运行时上下文里写着 danger-full-access. The DSH file sandbox does not restrict file modifications。

两道围挡，共享一张图纸

这是 dsh 沙箱最关键的设计。agent 改文件有两条路：一条是让 bash 命令去改（echo > file、sed -i），一条是让文件系统工具去改（edit、write 工具）。如果两道围挡各画各的图纸，就会出现"bash 能写但 fs 工具不让写"的分裂世界——agent 会困惑，会绕路，甚至被卡死在自相矛盾的权限里。

dsh 的解法是：一个统一的策略归属（ctx.sandboxPolicy）给每次能力调用解析一份完整策略，两道围挡拿的是同一张图纸。

bash 这道围挡（dsh-bash-sandbox）是内核级的。它把你要跑的命令 argv 包一层平台原生的隔离 runner——Linux 上优先用 bubblewrap，没有就用 Landlock；macOS 上用 sandbox-exec（Seatbelt）；Windows 上用 ACL 受限令牌。命令真正执行前，runner 就在内核层把"能写哪些路径"的围挡立好了。进程跑起来后，它和它 spawn 的所有子进程都逃不出这个围挡。

fs 这道围挡（dsh-fs-sandbox）是进程内的。它继承自本地文件系统后端，在每次 writeText/editText 调用前，先把目标路径"规范化"——解析符号链接、拼出真实绝对位置——然后比对"这个真实位置在可写集合里吗"。不在就返回一个结构化的 FS_SANDBOX_DENIED 错误。它不是内核级隔离，而是可信代码里的一道闸。reads 永远放行——所有模式都允许读。

两道围挡用的是同一个 writableRoots() 函数算出来的可写集合，所以它们永远不会对"同一个路径能不能写"给出不同答案。这就是"共享一张图纸"的字面含义——不是比喻，是代码里一个共享函数确保的。

举例 · 两条路被挡，体验一致

agent 在 workspace-write 下跑 bash -c "echo hi > /etc/hosts" → Linux runner 在内核层拒绝，stderr 出现 EROFS/EACCES 字样 → bash 工具认出这是沙箱拒绝（不是命令本身的报错），返回 [sandbox: file access denied under workspace-write mode]。

agent 改用 edit 工具改 /etc/hosts → fs 围栏在进程内拒绝，返回结构化的 FS_SANDBOX_DENIED → 工具层渲染成同一句 [sandbox: file access denied under workspace-write mode]。

两条路被挡的体验完全一致，agent 不会因为换了工具就遇到不同的权限逻辑。

拒绝是事实，升级走审批

沙箱的拒绝不是错误，是结果事实。被挡的命令照常返回，只是结果里多一行标记，告诉 agent "你被挡了，挡你的是哪个模式"。agent 拿到这个事实后可以决定怎么办——换个路径、放弃、或者申请升级。这个设计选择很关键：拒绝不抛异常、不中断对话，agent 可以像处理任何其他命令失败一样自然地处理它。

内置的一条出路是一次性升级。流程是这样的：被挡后，结果里除了拒绝标记，还附带一句升级提示——可以带 sandbox_permissions（要哪一档更宽的权限）加 justification（一句话说明为什么这条命令需要更宽）重试一次。重试时，系统先走审批服务（ctx.approval）。在交互场景里，这会弹一个审批卡问用户；在自动化场景里，由客户端的程序策略决定。审批通过，这一次调用按更宽模式执行，只对这一次有效，不改变会话的常驻模式。审批被拒或取消，直接失败，不能反复试。

这里有一条铁律：升级不能预先猜、不能反复试。agent 不能在还没被挡的时候就先带上最高权限"以防万一"，也不能被拒一次后换着花样重试绕过去。被拒一次就是终局。这个约束把升级限定在"确实被挡了、确实需要更宽、用户确实同意了"这个窄路径上，防止 agent 把升级当成常规手段滥用。

举例 · git push 的升级

agent 要 git push，需要读取并使用 ~/.ssh 里的密钥和 ~/.gitconfig，这些都在工作区外 → 在 workspace-write 下被 bash 围挡拦住。

agent 带上 sandbox_permissions: "danger-full-access" 加 justification: "git push 需要读取并使用 ~/.ssh 密钥和 ~/.gitconfig，这些在工作区外" 重试 → 审批卡弹给你 → 你点"通过" → 这一次 push 按 danger-full-access 执行 → push 完了，下一次命令又回到 workspace-write。

fail-closed 铁律

如果系统根本找不到能用的隔离 runner——比如 Linux 上既没装 bubblewrap，内核也不支持 Landlock——它直接报 SANDBOX_UNAVAILABLE 拒绝执行，绝不会静默地不放围挡就跑。宁可干不了，也不裸奔。这是整个沙箱设计的安全底线：受约束的执行要么真的被约束，要么不执行，不存在"约束没生效但还是跑了"这个状态。

边界与收尾

一句话总结

dsh 沙箱 = 三档文件效果权限 × 两道共享同一张图纸的围挡（bash 内核级 + fs 进程内）× 拒绝即事实加一次性审批升级 × fail-closed。它管的是"文件能落到哪"，不是通用安全沙箱。

最后说清这套沙箱的边界，避免误用。它管的是"文件能落到哪"，不是通用安全沙箱——网络访问、进程可见性、系统调用、设备访问都不在它的词汇表里。它也不做容器级隔离：bubblewrap、Landlock、Seatbelt 都是"同世界"的围挡，共享宿主文件系统和内核；真正的容器、microVM、远程执行是替换整条能力链（ctx.shell、ctx.fs），而不是往这个 seam 加一个 provider。

Windows 上的 ACL 围挡是"部分强制"（enforcement: 'partial'）——受限令牌必须保留 Everyone 组用于进程初始化，所以外部对象如果给 Everyone 授了写权限，就还能被写；NTFS 硬链接也会让一个文件对象同时出现在工作区内和工作区外。provider 会如实报告这个 partial，不会把边界吹成 full。对于需要绝对隔离不可信代码的场景，dsh 的立场是：文件围栏不是答案，那要靠 ctx.shell 配合容器级执行世界。这个 seam 有意把边界画在"够用且可移植"的位置上。
