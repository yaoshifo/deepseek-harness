一、一页总览：为什么值得看

一句话：记忆 = 本地纯文本文件 + 轻量索引 + 五个专用工具；机制只管「目录页」，不做记忆决策。

agent 默认跨会话失忆：这次纠正过的工作方式、说过的偏好、项目里的隐含约束，下个会话全部归零，只能靠人反复交代。dsh-memory 解决的就是这个问题——把值得记住的事落在本地文件里，让每个新会话带着一份「记忆的目录」开工。

这件事放在 DSH 的架构语境里看更有意义。DSH 是一个「全插件」的 agent 运行框架：系统提示组装、工具注册表、对话循环、会话日志，每一样都是框架里可插拔的服务。要扩展 agent 的能力，就是写一个插件把自己的贡献物「挂」到这些服务上，引擎本身一行不用改。dsh-memory 正是这样挂上去的：它是纯 opt-in 的可选插件，所有官方发布形态都不含它，哪个部署需要就由哪个部署挂载——「改引擎」和「带插件」是两码事，这是 DSH 扩展性的基本盘。

全文围绕五条设计主张展开，后面每一条都有一节的细节支撑：

1文件式，不建数据库——记忆是人和 agent 都能直接读写的纯文本，随时可看、可改、可备份。
2两级召回——常驻上下文的只有索引，正文按需读取：用极小的固定成本换「知道有什么」，而不是「什么都塞进来」。
3双作用域，写时自选——项目/全局靠一道判断题划分，拿不准时保守地记在项目侧。
4冲突靠规则，不靠仲裁——两套记忆打架没有自动裁决器；机制把判定规则教给 agent，在写入和搬移时执行；用户的显式指令永远最高优先。
5教科书式的插件形态——三个扩展点、显式配置、可逆注册、注入可回放，是理解「DSH 插件长什么样」的最佳样本（第六节）。

二、记忆长什么样

一事一文：每条记忆一个 Markdown 文件；索引是唯一每个会话都自动进入上下文的东西。

每条记忆是记忆目录里的一个 Markdown 文件，只装一件事。文件开头是几行元信息：名字、一句话摘要（description）、类型（user / feedback / project / reference）。agent 写入时，机制自动在元信息里补上「这是记忆、来自哪个会话」两条来源标记——机制只做加法，绝不改写正文。正文里鼓励用 [[别的记忆名]] 互链；链了但目标还不存在也没关系，那标记的是「有件事值得将来记」。

图 2 · 一条记忆（左）与它的索引行（右）：索引行是「目录页」，正文是「书页」，指针按链接指向定位

索引和正文的关系，就是「目录页」和「书页」的关系：索引每个会话开始时整体注入上下文（有预算上限）——这是 agent「知道自己记得什么」的唯一自动通道；正文不会自动注入，agent 判断相关后才用 memory_read 单独读取。所以索引里那行「标题 — 一句钩子」是整个机制的临门一脚：标题负责「是什么」，钩子负责「什么时候需要它」；一行写得含糊，这条记忆大概率永远不会被召回。

四类记忆：各记各的事

类型记什么例子
user用户是谁：角色、专长、偏好用户主要用中文沟通，偏好结论先行
feedback用户对工作方式的纠正与认可——必须带上为什么没跑测试前不要声称修复完成；上次因此误报过
project进行中的工作、目标、约束——从代码和 git 历史里推不出来的那些重构分支预计 9 月合并，依赖上游某版本发布
reference外部资源指针某个看板地址、某个工单链接

两条附加纪律：feedback / project 类记忆要在正文里跟 Why: 和 How to apply: 两行；project 类记忆里的相对日期要写成绝对日期（「上周」→ 具体日期），否则隔几个月召回时会失真。仓库里已有的信息（代码结构、修复历史、项目说明文件）明确不进记忆——从仓库读永远比从记忆读可靠。

图 3 · 两级召回的成本结构：索引以「每条一行」常驻，正文只有被判相关的才进上下文

五个记忆工具：唯一的读写通道

工具职责
memory_list列出记忆目录里所有文件（名字、大小、修改时间）
memory_read原样读一个文件（索引或任意记忆正文）
memory_write整文件替换写入一条记忆
memory_delete删除一个记忆文件
memory_index在索引里挂上/摘掉某条记忆的指针行

每个工具都接受可选的 scope 参数（默认 project，可传 global）。在标准沙箱策略下，它们是读写记忆目录的唯一通道：记忆目录在会话工作区之外，通用文件工具被文件沙箱拦住；记忆工具则直连宿主机文件系统——这样设计的取舍在第六节展开。存储位置完全本地：一个可配置的记忆根目录，里面每个项目一个子目录，外加一个全局目录，全是纯文本，随时可打开看、手动编辑、打包备份，手动改动下次会话直接生效。

三、记忆怎么写入

三道判断 + 两步落地：判断层（该不该记、记哪、会不会重复）由 agent 按策略执行；落地层（写文件、挂索引）由工具保证安全。

图 4 · 写入流水线：agent 过三道判断关，工具负责把最后两步安全落地

第一关是「该不该记」。策略里有一份负面清单：仓库已经记录的（代码结构、修过的 bug、git 历史、项目说明文件）不记；只对当前对话有意义的细节不记——会话结束了它就是噪音。用户说「记住这个」而内容恰好在负面清单里时，agent 会追问「这里面非显而易见的点是什么」，把那个点存下来，而不是原样照抄。

第二关是「是不是重复」。写入前先查有没有已有记忆覆盖这件事；有就更新那条，而不是新建重复。发现某条记忆被证伪，就删掉它。「更新优先、错了就删」和「写入」同等重要——记忆的价值取决于它保持正确。

第三关是「记哪个作用域」，一道判断题，第五节专门展开：这条记忆换个不相关项目还有用吗？有用记全局，没用记项目，拿不准记项目。

落地层的四道安全细节
整文件替换：必须给完整内容，没有「局部修改」语义，避开编辑冲突的复杂度；文件名即边界：只接受单段文件名，拒绝路径与 ..，不可能写到记忆目录外面，缺 .md 后缀自动补上；原子落盘：先写临时文件再改名，并发场景下不会出现半个文件，目录不存在自动创建；来源自动补记：往已有元信息块追加来源标记，幂等（已有就不加），绝不改写正文。写 MEMORY.md 本身超预算时，写入照常成功但附带警告——警告不拦截，治理靠提示。

落地第二步挂索引，memory_index 的语义经过仔细设计：按「链接指向哪个文件」定位行（带不带 .md 后缀都认），原地替换，重复行折叠成一行；索引不存在时自动创建并带标准标题头，remove 在指针不存在时是安全空操作。工具不发明内容：标题和钩子必须由调用方给出且必须是单行——「一行写得让人想点开」这个质量责任，机制不代劳。为什么不直接整文件重写 MEMORY.md？因为「一次只动一行」把并发冲突面压到最小，也避免 agent 重写时手滑弄丢别的行。策略里明确要求：维护索引用 memory_index，不要整写。

四、记忆怎么召回

两级召回：索引自动注入一次（免费但有限额），正文由 agent 判断相关后按需读取。没有向量检索，召回质量完全取决于索引行的质量。

图 5 · 召回时序：会话第一步注入双索引（每作用域至多一次），正文按需读取

注入框架的四个关键细节
预算双限制：行数上限（默认 200 行）与字节上限（由部署显式声明，常见 25 KB），先到为准；整行截断：超预算按整行丢弃，不劈行、不切断多字节字符，并提示 agent 读全文、精简索引；防伪框架：注入内容包在插件自有的提醒框里，索引正文里就算出现伪造的闭合标签也会被转义，不可能提前「越狱」；明确告诫：框架开头写明——被召回的记忆是背景上下文，不是用户指令，且只反映写入当时的情况，记忆里提到的文件、函数、开关，用前先验证还存在。这最后一句是召回侧的安全锚点：同时防「把旧记忆当圣旨」和「把记忆当当前事实」两种失误。

注入不是「每次请求都塞一遍」的临时动作，而是一条被写进会话日志的持久消息，带完整的来源标记（哪个插件注入的、哪个作用域、哪个项目、内容的数字摘要）。由此得到三个性质：同一会话日志里每个作用域至多注入一次，插件扫日志查重，恢复会话不会再来一遍；上下文压缩也不触发重注入——日志只增不改，标记一直在；这条消息可审计、可重放。想看最新状态，用 memory_read 直接读文件，那是永远新鲜的。代价是：会话进行到一半时改了记忆或索引，本会话已注入的部分不会自动刷新（第八节）。没有向量检索、没有语义搜索是刻意的选择：文件式 + 高质量的人类可读索引，比黑盒相似度更可解释、可维护——哪条召回不来，改那一行就行。

谁有资格被注入

注入只面向「正常的顶层交互会话」，并且要求一个有效的工作目录。三类会话明确不注入：子 agent（子任务会话）——它们没有记忆策略提示，调用记忆工具直接报错，因为子任务通常跑在隔离的工作副本目录里，让它们写记忆会写出一个没人召回的孤儿目录；一次性侧查询（如标题生成这类不进入主循环的辅助问答）——它们把全部上下文带在问题里，注入索引反而是噪音；没有（或非标准）工作目录的会话——项目记忆目录由工作目录派生，派生不了就不猜，宁可不注入。另外，全局作用域默认开启，部署可以用配置整体关掉它：关掉后相关提示消失、不再注入全局索引、工具也不接受全局参数。

五、双作用域：划分与冲突

一道判断题 + 一个保守默认；没有自动仲裁，规则教给 agent 执行，用户的显式指令永远最高优先。

图 6 · 作用域判断题：拿不准默认记项目，用户显式指令可随时推翻

判断题只有一句：这条记忆，在一个完全不相关的项目的会话里，还有用吗？有用记全局——全局只收「放在哪都成立」的事实：用户是谁、喜欢怎么协作、这台机器和这套框架本身的坑；没用记项目——一切绑定在这个仓库上的东西（代码、约定、历史、运维）留在项目记忆。这条规则被刻意放在离决策点最近的三个地方重复出现：提示词里的全局记忆附录（写之前看）、scope 工具参数的描述（选的时候看）、全局索引注入的框架头（召回时看）——保证 agent 在「写」和「读」两个时刻都拿着同一把尺子。

为什么拿不准记项目：不对称代价下的保守选择
记窄了（该进全局的进了项目）：损失只是别的项目召回不到它——局部损失。记宽了（该留项目的进了全局）：它会被注入到这台机器上将来跑的每一个会话里——全局污染。「局部缺一条」和「条条会话背噪音」相比，显然前者便宜得多。
举例

「这台机器上 git 推送被沙箱拦时，先提权试钥匙串、再怀疑凭证失效」——这类机器与框架级的坑换个项目照样成立，记全局；「重构分支预计 9 月合并，依赖上游某版本发布」——离开这个仓库就无关，记项目。后者若误记进全局，就会出现在这台机器上每一个会话的索引里。

两个作用域打架了怎么办？直接回答：没有任何自动仲裁、后台合并或定时整理进程。记错边、两边重复，都靠 agent 执行一套明确教给它的规则来纠正。

图 7 · 冲突三规则：写时预防、惰性搬移、跨作用域去重；刻意不做后台自动整理

为什么不建一个定时自动晋升/清理的进程？两个理由。其一，写时和惰性路径的上下文更充分——agent 正在处理具体任务，它知道这条记忆为什么存在、是否仍然成立，后台扫描没有这些信息；其二，全局内容会注入所有会话，属于高影响面区域——无人值守的自动写入等于绕过人工把关。宁可让去重「机会主义地」发生，也不建一个会自己往全局里写东西的进程。如果将来误归档真的频繁，规划的升级路径是「按需审计」（一个手动触发的整理动作），而不是常驻后台任务。

作用域之外还有另一类冲突：记忆与现实的冲突（记过时了、记错了）。同样没有仲裁器，靠三层防线：写入侧，更新优先于新建，被证伪的记忆直接删除；召回侧，注入框架的告诫明确「记忆只反映写入当时的情况，用前先验证」；格式侧，元信息不做 schema 强制校验（缺字段不会报错），机制只做加法回填——格式的纪律交给策略层，与「机制不替 agent 做记忆决策」的总原则一致。记忆的正确性是持续治理出来的，不是一次写入保终身。

六、插件工程范本的价值

对想写 DSH 插件的团队，dsh-memory 用很小的代码踩满了所有模型可见的扩展点：三个钩子、显式配置、可逆注册——它是「DSH 插件长什么样」的标准模板。

图 8 · dsh-memory 挂在 DSH 引擎上的三个扩展点，外加「注入 = 持久日志事件」的落点

函数型插件就是四个导出，各司其职：

导出职责dsh-memory 的取值
name插件名（加载诊断用）dsh-memory
inject依赖的服务列表（激活顺序由此表达）tools、systemPrompt、agents
Config配置 schema，加载期校验，非法值直接启动失败记忆根目录、索引预算、全局开关
apply注册所有贡献物提示词段 + 五个工具 + 事件监听（另有伴生日志校验插件）

两条铁律：没有 default 导出（形态混用会让加载器丢掉插件的命名空间）；apply 里每次注册都是可逆副作用，返回销毁器——插件卸载/热重载时一切自动撤除，且有专门测试验证「销毁后一切消失」。配置设计同样值得一抄：注入上下文的预算是必填项，没有默认值——「往模型上下文里放多少东西」必须由部署显式声明，插件不偷偷决定；全局作用域默认开启、全局预算默认继承项目预算——一次显式声明同时治理两个作用域；非法配置在加载期就失败，绝不静默回退。

插件怎么被装进一个运行形态？DSH 的组合是分层 patch：官方 bundle（基础层 / GUI 层 / 无头层…）→ 部署 profile 的补丁层 → 用户主目录层 → 命令行 overlay，逐层叠加出最终的插件树。往一个部署里加插件，就是 profile 补丁文件里写一段插入（声明插件名和配置），然后用 dump-config 命令查看最终插件树来验证——引擎代码零改动。

图 9 · 四层组合出最终插件树：加插件只动 profile 补丁层，不碰引擎

五条值得抄的设计取舍

1直连宿主文件系统，不走可替换的 fs 能力。理由：记忆必须「在哪台机器跑就在哪台机器」，无论部署形态怎么变。代价：绕开了沙箱与可替换性，于是工具内部自建信任边界（文件名单段校验，杜绝路径逃逸）。守则：绕过通用能力时，必须自己补上等价的边界。
2顶层会话专属，且在每个入口各自把关。「只有顶层会话有记忆」同时落在三处：提示词段返回空、注入跳过、工具报错。教训：规则不能只挡一个入口——判定必须落在真正做决定的那个操作里。
3注入 = 带来源标记的持久会话事件。换来可重放、可查重、可审计三样东西，外加伴生校验插件在每次加载/追加时检查结构不变量。凡是模型可见的注入都该走这条路，而不是每次请求现拼——后者既不可回放，也破坏缓存。
4fail loud 与优雅跳过各就各位。配置非法、参数非法、越权调用、作用域未启用——一律响亮报错；唯独会话启动时读索引的瞬时失败选择跳过该次注入。分界线：能归因到具体调用的错误就地报；属于环境抖动的，延迟到真正需要时再报。
5注册皆可逆 + 成本文档化。插件销毁后工具、提示段、监听器必须全部消失；「模型体验」——模型看到什么、每请求的 token 成本、对缓存前缀稳定性的影响——写进包文档。注入型插件直接影响缓存复用，这是新手最容易漏记的一笔账。
附：写第一个 DSH 插件的十项检查清单
  1. 先想清楚贡献物落在哪个注册表：常驻指令→提示词段；模型可调用的能力→工具；按步改消息→agent 事件；非模型可见的副作用→对应能力/会话事件。
  2. 四导出形态，无 default；配置过 schema 校验，非法值加载期失败。
  3. 一切注册走 effect 拿销毁器（注册即登记撤销方法）；为「销毁后一切消失」写测试。
  4. 注入模型上下文的内容，用带自有来源标记的持久消息，配伴生校验插件。
  5. 工具返回规范化 JSON 值；参数校验交给框架，框架表达不了的约束自己查；尊重取消信号。
  6. 往上下文里注入的东西，预算由部署显式声明，不藏默认值。
  7. 条件性贡献在每个入口各自把关，别指望一处拦截全局生效。
  8. 组合进部署走 profile 补丁层，不碰引擎；用 dump-config 验证。
  9. 绕过某个通用能力（沙箱、可替换 provider）时，自己补上等价的边界。
  10. 文档写清模型体验与已知边界——已知边界不丢人，它是给下一个部署者的地图。

七、领导关心的问答

以下按主题归组整理使用方与插件作者的高频问题；默认折叠，点开即读。结论性的内容已在正文各节给出。

存储与隐私

Q：记忆数据存在哪里？团队可以自己查看、修改和备份吗？

全部存在 agent 所在机器的本地文件系统：一个可配置的记忆根目录，每个项目一个子目录，外加一个全局目录。内容是纯文本 Markdown，随时可打开查看、手动编辑、打包备份；机制每个会话读的都是文件当下的内容，手动改动下次会话直接生效。

Q：记忆会上云、会被别的机器共享吗？

存储完全本地：插件刻意直连宿主机文件系统，任何部署形态下记忆都不出本机。需要说明：被读取的记忆内容会随模型请求发往模型服务，这是一切 LLM 记忆机制的固有属性，与存储位置是两回事。

成本与上下文

Q：新会话是怎么「想起来」的？是把所有记忆全塞进上下文吗？

不是。只有索引（MEMORY.md）在会话开始时注入一次，且有行数与字节双重预算；每条记忆的正文等 agent 判断与当前任务相关后才单独读取。两级结构的意义：用极小的固定成本换「知道自己记得什么」。

Q：为什么不直接把全部记忆文件注入上下文？

记忆会持续累积，全量注入很快撑爆上下文，而且大部分内容与当前任务无关。索引把成本压成「每条记忆一行」，用最小占位换「知道有什么」；正文成本只花在被判断相关的那几条上。

Q：索引太大了会怎样？

双重预算（默认 200 行，加部署声明的字节上限，常见 25 KB）超出即整行截断，并提示 agent 读全文、把索引精简回去；往索引写入超预算内容时也会收到警告。「一行一钩子、细节进正文」的索引治理是使用方的长期功课。

正确性与并发

Q：全局和项目两边记重了、记错位置了，有自动仲裁吗？

没有自动仲裁，纠错规则交给了 agent：发现项目记忆其实跨项目，就按四步搬移到全局；同一事实两边都有，删掉放错边那份、按判断题留对的；使用方的显式指令随时可以强推。刻意不做后台自动整理——全局内容会注入这台机器上所有会话，无人值守写入等于绕过人工把关。

Q：记忆过时了、记错了怎么办？

三层防线：写入时更新优先于新建；召回时注入框架明确告诫「记忆只反映写入当时的情况，用前先验证」；发现被证伪的记忆直接删除。记忆的正确性靠持续治理，不是一次写入保终身。

Q：多个会话同时写记忆，会冲突吗？

单个文件层面安全：写入是原子操作（临时文件加改名），不会出现半个文件。文件内容的并发修改是「后写覆盖先写」，与同时编辑两份普通文本文件同一语义；索引维护被刻意做成「一次只动一行」，把冲突面压到最小。

使用边界

Q：记忆是 agent 自动记的，还是每次都要人工交代？

默认自动：agent 按内置策略自己判断什么值得记（用户偏好、纠正反馈、项目约束等），显式指令永远优先。它同时有自律边界——仓库里已有的信息、只对当前对话有意义的细节不记；被要求记这类内容时，它会先追问「非显而易见的点是什么」，然后只存那一个点。

Q：什么内容不该进记忆？

三类：仓库本身已记录的内容（代码、修复历史、项目说明文件），从仓库读比从记忆读可靠；只对当前对话有意义的临时细节；说不清「为什么值得记」的内容。

Q：一条记忆拿不准放全局还是放项目，怎么办？

记项目。判断题是「换个不相关项目还有用吗」，但拿不准时默认项目侧：记窄了只是别的项目召回不到，属局部损失；记宽了会污染这台机器上所有会话，是全局损失。

Q：子 agent（子任务）能用记忆吗？

不能，这是有意设计。子任务跑在隔离目录里，允许它们写记忆会产生没人召回的孤儿目录，调用记忆工具会直接报错；记忆只属于顶层会话。

Q：恢复会话、压缩上下文之后，记忆注入还在吗？会重新注入吗？

在，且不会重注。注入是写进会话日志的持久事件（带来源标记和内容摘要），恢复会话时随日志重放，插件按日志去重、每个作用域至多注入一次，压缩上下文也不触发重注入。会话中途要看最新记忆，直接让 agent 调用 memory_read。

与项目文档的分工

Q：记忆和项目里的说明文件（AGENTS.md 那类）有什么区别？

说明文件是仓库的一部分：进版本库、团队共享、每次会话整体生效，适合「这个项目怎么干」的稳定约定。记忆是 agent 的个人笔记本：不进仓库、按相关性召回、随时增删，适合「从仓库推不出来的事」；策略明确禁止把仓库已记录的内容搬进记忆，两者是分工不是冗余。

插件作者速查

Q：一个 DSH 插件最小长什么样？

四个导出：name、inject（声明依赖的服务）、Config（配置 schema）、apply（注册逻辑），没有 default 导出，apply 里每次注册都返回销毁器。一个几十行的插件就能给 agent 挂上工具和常驻指令。

Q：dsh-memory 一共挂了哪几个钩子？

三类各一个：提示词段（常驻记忆策略，order 110）、五个 memory_* 工具（schema 自动进系统提示）、一个 agent 事件监听（会话第一步注入索引）。加上配置与一个伴生日志校验插件，全部贡献就这些。

Q：插件怎么被装进一个运行形态？

插件树由 bundle、profile 补丁层、用户层、命令行 overlay 逐层组合而成；加插件就是在 profile 补丁文件里写一段 insert 声明插件名和配置，再用 dump-config 命令验证最终树，引擎代码零改动。dsh-memory 本身纯 opt-in，官方 bundle 都不含它，由各部署自行挂载。

Q：注入为什么做成「持久会话事件」，而不是每次请求现拼？

持久事件可重放、可查重、可审计：恢复会话时历史从日志派生，「每个作用域至多一次」靠扫日志强制，来源标记加内容摘要由伴生插件校验结构不变量。硬原则是「模型可见的内容必须能从会话日志重建」，现拼既回放不出，也破坏缓存。

Q：它的文件操作为什么不走沙箱和可替换的 fs 能力？

记忆必须落在宿主机本地，不随部署形态（沙箱、远程、容器）改变，直连宿主文件系统是刻意豁免；豁免的代价是自建信任边界，文件名单段校验杜绝路径逃逸。副产品：通用文件工具被沙箱挡在记忆目录外，记忆工具成为唯一写通道。

Q：配置为什么把索引预算设成必填？

向模型上下文注入多少内容是部署级的成本决策，插件不替部署做主；必填且全局预算默认继承项目值，一次显式声明、两个作用域都有上限。非法配置加载期直接失败，绝不静默回退到默认值。

Q：写插件最容易踩的坑是什么？

按常见程度排：注册没走 effect 导致热重载残留、条件性贡献只挡一个入口、注入模型上下文缺会话事件兜底、漏算 token 与 KV cache 成本、绕过通用能力却不补边界校验。

八、已知边界与取舍

边界都摆在明面上：多数是「有意为之」的设计取舍，一项是已排期的改进项——没有隐藏的坑。

边界现状性质
并发写同一文件后写覆盖先写（写入本身原子，不会出半个文件）；无文件锁与并发编辑普通文件同语义，接受
Windows 工作目录不支持：无提示段、无注入、工具响亮报错有意——目录派生规则未在那类路径上验证，宁可失败不猜
会话中途索引不重载本会话内改动索引/记忆，已注入部分不刷新有意——一次性注入换缓存前缀稳定；要最新状态用 memory_read
无「接近预算」提醒只有写入超预算后的警告，没有临近提醒已知改进项（补充式提醒，不影响格式）
元信息无格式强制frontmatter 缺字段不报错，机制只做加法回填有意——格式纪律交给策略层，与「机制不替 agent 做记忆决策」一致
无定时项目→全局晋升搬移/去重只由 agent 按规则机会主义执行有意——见第五节；升级路径是按需审计而非后台进程
跨作用域去重无工具强制规则只存在于提示词与注入框架文案，无后台对账有意——同上
