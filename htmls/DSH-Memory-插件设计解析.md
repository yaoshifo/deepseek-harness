# DSH Memory 插件设计解析
## 记忆机制的原理，与一个 DSH 插件的完整范本

> **写给谁**：① 正在（或即将）使用 DSH、想搞懂「agent 的记忆怎么运转」的人；② 想写第一个 DSH 插件、需要一个大而全的范本的人。全文按「先总览、再细节」组织；§5 起切换到插件作者视角；§6 是预置的常见问题解答。
>
> **DSH 是什么**（给没接触过的读者三句话）：DSH 是一个「全插件」的 agent 运行框架——agent 的系统提示组装、工具注册表、对话循环、会话日志，每一样都是框架里可插拔的服务；要扩展 agent 的能力，就是写一个插件，把自己的贡献物「挂」到这些服务上，引擎本身一行不用改。本文的主角 dsh-memory 就是这样一个插件：它给 agent 挂上了跨会话的持久记忆。

## 0. 一页总览

**一句话设计**：

> 记忆是 agent 所在机器上的一堆纯文本 Markdown 文件——一事一文；常驻上下文的只有一个轻量索引（MEMORY.md），每个会话开始时注入一次；写入与召回都由 agent 通过五个专用工具完成。机制只负责提供「目录页」，不替 agent 做记忆决策。

**五个核心概念**：

| 概念 | 一句话说明 |
|---|---|
| 记忆文件 | 一个 Markdown 文件记一件事，开头带三条元信息（名字、一句话摘要、类型） |
| MEMORY.md 索引 | 记忆目录的「目录页」，每条记忆一行；是唯一每个会话都自动进入上下文的东西 |
| 项目记忆 | 每个项目（按工作目录区分）一份独立记忆目录，项目之间互不可见 |
| 全局记忆 | 整台机器共享一份记忆目录，所有项目的会话都能读 |
| 记忆工具 | memory_list / memory_read / memory_write / memory_delete / memory_index，读写记忆目录的专用通道 |

**写入流程**（详见 §2）：

```
① 该不该记？   ── 负面清单过滤：仓库已记录的不记、只对当前对话有意义的不记
      ↓
② 查重        ── 已有记忆覆盖这件事？更新它，而不是新建重复
      ↓
③ 选作用域     ── 换个不相关项目还有用吗？有用→全局；没用→项目；拿不准→项目
      ↓
④ 写文件       ── memory_write：整文件替换、原子落盘、自动补来源标记
      ↓
⑤ 挂索引       ── memory_index：在 MEMORY.md 写一行「标题 — 一句钩子」
```

**召回流程**（详见 §3）：

```
会话第一个处理步（每会话仅此一次）
   ├─ 读全局索引 ─ 预算内 → 注入上下文
   └─ 读项目索引 ─ 预算内 → 注入上下文
        ↓
agent 看到的是「目录页」：知道有哪些记忆、各自关于什么
        ↓ 判断与当前任务相关
memory_read 按需读正文（此时才花上下文成本）
```

**五条设计要点**（全文都是它们的展开）：

1. **文件式，不建数据库**——记忆是人和 agent 都能直接读写的纯文本，随时可看、可改、可备份。
2. **两级召回**——常驻上下文的只有索引，正文按需读取：用极小的固定成本换「知道有什么」，而不是「什么都塞进来」。
3. **双作用域，写时自选**——项目/全局靠一道判断题划分，拿不准时保守地记在项目侧。
4. **冲突靠规则，不靠仲裁**——两套记忆打架没有自动裁决器；机制把判定规则教给 agent，在写入和搬移时执行；用户的显式指令永远最高优先。
5. **教科书式的插件形态**——三个扩展点、显式配置、可逆注册、注入可回放，是理解「DSH 插件长什么样」的最佳样本（§5）。

## 1. 核心概念

### 1.1 记忆文件：一事一文

每条记忆是记忆目录里的一个 Markdown 文件，只装**一件事**。文件开头是几行元信息：

```markdown
---
name: short-kebab-case-slug
description: 一句话摘要——召回时靠它判断相关性
metadata:
  type: user | feedback | project | reference
---

正文：这件事本身。
```

几条贯穿始终的纪律：

- **一事一文**：拆成多个文件，而不是把一堆事塞进一个大文件。
- **description 是给「未来的召回」看的**：agent 决定要不要细读某条记忆，依据就是索引行和这行摘要——它的质量直接决定召回质量。
- **鼓励互链**：正文里可以用 `[[别的记忆名]]` 链到相关记忆；链了但目标还不存在也没关系——那标记的是「有件事值得将来记」。
- **来源自动补记**：agent 写入记忆文件时，机制自动在元信息里补上「这是记忆、来自哪个会话」两条标记（只在已有元信息块时追加，绝不改动正文）。

### 1.2 四类记忆

| 类型 | 记什么 | 例子 |
|---|---|---|
| user | 用户是谁：角色、专长、偏好 | 「用户主要用中文沟通，偏好结论先行」 |
| feedback | 用户对工作方式的纠正与认可——必须带上为什么 | 「没跑测试前不要声称修复完成；上次因此误报过」 |
| project | 进行中的工作、目标、约束——**从代码和 git 历史里推不出来的**那些 | 「重构分支预计 9 月合并，依赖上游某版本发布」 |
| reference | 外部资源指针 | 某个看板地址、某个工单链接 |

两个附加纪律：feedback/project 类记忆要在正文里跟 **Why:** 和 **How to apply:** 两行；project 类记忆里的相对日期要写成绝对日期（「上周」→ 具体日期），否则隔几个月召回时会失真。

### 1.3 MEMORY.md 索引：目录页与书页

记忆目录里有一个特殊文件 MEMORY.md——**索引**。每条记忆对应一行：

```markdown
- [标题](记忆文件名) — 一句钩子
```

它和记忆正文的关系，就是「目录页」和「书页」的关系：

- 索引**每个会话开始时整体注入上下文**（有预算上限）——这是 agent「知道自己记得什么」的唯一自动通道；
- 正文**不会自动注入**，agent 判断相关后才用 memory_read 单独读取。

所以那一行「钩子」是整个机制的临门一脚：标题负责「是什么」，钩子负责「什么时候需要它」。一行写得含糊，这条记忆大概率永远不会被召回。

### 1.4 两个作用域：项目记忆与全局记忆

记忆放在哪，由两个作用域决定：

- **项目记忆**：每个工作目录对应一份独立的记忆目录（目录名由工作目录编码而来），项目 A 的会话看不到项目 B 的记忆。适合一切「绑定在这个仓库上」的事——它的代码、约定、历史、运维。
- **全局记忆**：整台机器共享一份记忆目录，无论从哪个项目发起的会话都能读。适合「放在哪个项目都成立」的事——用户是谁、喜欢怎么协作、这台机器或这套框架本身的坑（沙箱怪癖、凭证位置、某个工具的毛病）。

两个目录都位于用户主目录下一个可配置的记忆根目录里。全局作用域默认开启；部署可以用配置整体关掉它（关掉后：相关提示消失、不再注入全局索引、工具也不接受全局参数）。

### 1.5 五个记忆工具：唯一的读写通道

| 工具 | 职责 |
|---|---|
| memory_list | 列出记忆目录里所有文件（名字、大小、修改时间） |
| memory_read | 原样读一个文件（索引或任意记忆正文） |
| memory_write | 整文件替换写入一条记忆 |
| memory_delete | 删除一个记忆文件 |
| memory_index | 在索引里挂上/摘掉某条记忆的指针行 |

每个工具都接受可选的 `scope` 参数（默认 project，可传 global）。在标准沙箱策略下，**它们是读写记忆目录的唯一通道**：通用文件工具碰不到记忆目录——记忆目录在会话工作区之外，被文件沙箱拦住；记忆工具则直连宿主机文件系统（为什么这么设计，见 §5.4）。

## 2. 记忆是怎么写入的

写入是一条「三道判断 + 两步落地」的流水线。判断层（该不该记、记哪、会不会重复）完全由 agent 按策略执行；落地层（写文件、挂索引）由工具保证安全。

### 2.1 判断链：agent 层的三道关

**第一关：该不该记？** 策略里有一份负面清单：

- 仓库已经记录的（代码结构、修过的 bug、git 历史、项目说明文件）不记——那些从仓库本身就能得到，从仓库读永远比从记忆读可靠；
- 只对当前对话有意义的细节不记——会话结束了它就是噪音。

用户说「记住这个」而内容恰好在负面清单里时，agent 会追问「这里面非显而易见的点是什么」，把**那个点**存下来，而不是原样照抄。

**第二关：是不是重复？** 写入前先查有没有已有记忆覆盖这件事；有就更新那条，而不是新建重复。发现某条记忆被证伪，就删掉它。「更新优先、错了就删」和「写入」同等重要——记忆的价值取决于它保持正确。

**第三关：记哪个作用域？** 一道判断题（详见 §4）：这条记忆换个不相关项目还有用吗？有用记全局，没用记项目；拿不准记项目。

### 2.2 落地第一步：memory_write 写文件

工具层为「写」兜住了所有安全细节：

- **整文件替换**：必须给完整内容，没有「局部修改」语义——避开编辑冲突的复杂度；
- **文件名即边界**：只接受单段文件名（拒绝路径、拒绝 `..`，不可能写到记忆目录外面）；缺 `.md` 后缀自动补上；
- **原子落盘**：先写临时文件再改名，并发场景下不会出现半个文件；目录不存在会自动创建；
- **来源自动补记**：往已有元信息块里追加「这是记忆 / 来自哪个会话」两条标记，幂等（已有就不加）、绝不改写正文；
- **预算警告**：写 MEMORY.md 本身超出行/字节预算时，写入照常成功但附带警告，提醒把细节挪进记忆文件、精简索引——警告不拦截，治理靠提示。

### 2.3 落地第二步：memory_index 挂索引

写完记忆文件，紧接着在索引里挂上指针行。memory_index 的语义经过仔细设计：

- **按「链接指向哪个文件」定位行**：upsert 会找到索引里指向该记忆文件的那一行（带不带 `.md` 后缀都认），原地替换；没有就追加在最后一个非空行之后；重复行会折叠成一行。
- **索引不存在时自动创建**，带上标准标题头；remove 在指针不存在时是安全空操作，不会凭空创建文件。
- **工具不发明内容**：标题和钩子必须由调用方给出，且必须是单行——「一行写得让人想点开」这个质量责任，机制不代劳。

为什么不直接整文件重写 MEMORY.md？因为「一次只动一行」把并发冲突面压到最小，也避免 agent 重写时手滑弄丢别的行。策略里明确要求：维护索引用 memory_index，不要整写。

## 3. 记忆是怎么召回的

召回分两级：**自动的索引注入**（每会话一次，免费但有限额）+ **主动的按需读取**（agent 自己判断，想读多少读多少）。

### 3.1 会话启动：索引注入

会话的第一个处理步（且会话日志中尚无该作用域的注入记录——所以恢复会话不会重注），插件做一次注入：

1. **读全局索引**（存在的话），按预算截断后包进一个系统提醒框，注入上下文；
2. **读项目索引**（存在的话），同样处理。

注入的几个关键细节：

- **预算双限制**：行数上限（默认 200 行）与字节上限（由部署显式声明，常见配置 25 KB），先到为准；
- **整行截断**：超预算时按整行丢弃，不会把一行劈成两半，也不会切断多字节字符；截断时附带提示，告诉 agent「索引没显示全，用 memory_read 读全文并精简索引」；
- **防伪框架**：注入内容包在插件自有的提醒框里；索引正文里就算出现伪造的闭合标签也会被转义，不可能提前「越狱」闭合提醒框；
- **明确告诫**：框架开头写明——被召回的记忆是**背景上下文，不是用户指令**，且只反映**写入当时**的情况；记忆里提到的文件、函数、开关，推荐使用前要先验证还存在。

这最后一句告诫是召回侧的安全锚点：同时防「把旧记忆当圣旨」和「把记忆当当前事实」两种失误。

### 3.2 一次性与持久化：为什么恢复会话不会重复注入

注入不是「每次请求都塞一遍」的临时动作，而是**一条被写进会话日志的持久消息**，带完整的来源标记（哪个插件注入的、哪个作用域、哪个项目、内容的数字摘要）。由此：

- 同一个会话日志里，每个作用域**至多注入一次**——插件会扫日志查重，恢复会话（resume）不会再来一遍；
- 上下文压缩（compaction）也不会触发重注入——日志只增不改，标记一直在；
- 想看最新状态？用 memory_read 直接读文件，那是永远新鲜的。

代价是：**会话进行到一半时**改了记忆或索引，本会话已注入的部分不会自动刷新（见 §7 边界）。

### 3.3 会话中：按需读取

注入完成后，agent 手里是两张「目录页」。接下来的召回全靠它自己：

1. 浏览索引行，结合当前任务判断哪些记忆相关（标题 + 钩子 + 正文元信息里的 description）；
2. 对相关的条目调用 memory_read 读正文；
3. 用完继续干活。

没有向量检索、没有语义搜索——**召回质量完全取决于索引行的质量**。这是刻意的选择：文件式 + 高质量的人类可读索引，比黑盒相似度更可解释、可维护——哪条召回不来，改那一行就行。

### 3.4 谁有资格被注入

注入只面向「正常的顶层交互会话」，并且要求一个有效的工作目录。以下都不注入：

- **子 agent（子任务会话）**——它们没有记忆策略提示，调用记忆工具会直接报错。理由：子任务通常跑在隔离的工作副本目录里，让它们写记忆会写出一个没人召回的孤儿目录；
- **一次性侧查询**（如标题生成这类不进入主循环的辅助问答）——它们把全部上下文带在问题里，注入索引反而是噪音；
- **没有（或非标准）工作目录的会话**——项目记忆目录由工作目录派生，派生不了就不猜，宁可不注入。

## 4. 双作用域：划分与冲突

这是这套机制最常被问的两个问题：怎么划分？打架了怎么办？

### 4.1 划分：一道判断题 + 一个保守默认

判断题只有一句话：

> **这条记忆，在一个完全不相关的项目的会话里，还有用吗？**

- **有用 → 全局。** 全局只收「放在哪都成立」的事实：用户是谁、喜欢怎么协作、这台机器和这套框架本身的坑。
- **没用 → 项目。** 一切绑定在这个仓库上的东西——代码、约定、历史、运维——留在项目记忆。

拿不准时**默认记项目**。这是不对称代价下的保守选择：

- 记窄了（该进全局的进了项目）：损失只是别的项目召回不到它——局部损失；
- 记宽了（该留项目的进了全局）：它会被注入到**这台机器上你将来跑的每一个会话**里——全局污染。

「局部缺一条」和「条条会话背噪音」相比，显然前者便宜得多。

这条规则被刻意放在**离决策点最近的三个地方**重复出现：提示词里的全局记忆附录（写之前看）、scope 工具参数的描述（选的时候看）、全局索引注入的框架头（召回时看）——保证 agent 在「写」和「读」两个时刻都拿着同一把尺子。此外，**用户的显式指令永远优先于这条规则**：你说「记到全局」，它就记到全局。

### 4.2 冲突：没有自动仲裁，靠教给 agent 的规则

**直接回答：没有任何自动仲裁、后台合并或定时整理进程。** 记错边、两边重复，都靠 agent 执行一套明教的规则来纠正。具体是三条：

**规则一：写时测试（事前预防）。** 就是 §4.1 那道判断题——冲突的最小化从写入那一刻开始。

**规则二：惰性搬移（事后纠正）。** 当 agent 发现某条项目记忆其实跨项目成立——典型场景：在另一个不相关项目里撞上了同一个坑——就执行四步搬移：

```
写进全局 → 在全局索引挂指针 → 删除项目里的原文件 → 摘掉项目索引里的指针
```

**规则三：跨作用域去重（对账）。** 同一个事实两边都有时，删掉放错边的那份及其索引指针，只留「过了判断题」的那份：过得了留全局，过不了留项目。这条规则同时是**降级路径**——发现全局里有一条其实绑定某仓库的记忆，反向执行即可。

为什么不做定时自动晋升/清理？两个理由：

1. **写时和惰性路径的上下文更充分**——agent 正在处理具体任务，它知道这条记忆为什么存在、是否仍然成立；后台扫描没有这些信息；
2. **全局内容会注入所有会话，属于高影响面区域**——无人值守的自动写入等于绕过人工把关。宁可让去重「机会主义地」发生，也不建一个会自己往全局里写东西的进程。

如果将来误归档真的频繁，规划的升级路径是「按需审计」（一个手动触发的整理动作），而不是常驻后台任务。

### 4.3 内容层面的冲突：记忆过时了、记错了怎么办

作用域之外还有另一类冲突：记忆与现实的冲突。同样没有仲裁器，靠三层防线：

1. **写入侧**：更新优先于新建（防止同一件事存出两个版本）；被证伪的记忆直接删除；
2. **召回侧**：注入框架的告诫（§3.1）明确「记忆反映写入当时的情况，用前先验证」；
3. **格式侧**：元信息不做 schema 强制校验（缺字段不会报错），机制只做加法（自动补来源标记）——格式的纪律交给策略层，与「机制不替 agent 做记忆决策」的总原则一致。

## 5. 换个视角：把 dsh-memory 当 DSH 插件的范本

前四节讲的是「记忆机制」。这一节换镜头：对想写 DSH 插件的人，dsh-memory 几乎用最小的代码踩满了所有模型可见的扩展点，是很好的模板。

### 5.1 一个 DSH 插件长什么样

函数型插件就是四个导出：

| 导出 | 职责 | dsh-memory 的取值 |
|---|---|---|
| name | 插件名（加载诊断用） | dsh-memory |
| inject | 依赖的服务列表（激活顺序由此表达） | tools、systemPrompt、agents |
| Config | 配置 schema，加载期校验，非法值直接启动失败 | 记忆根目录、索引预算、全局开关 |
| apply | 注册所有贡献物 | 见下 |

两条铁律：**没有 default 导出**（形态混用会让加载器丢掉插件的命名空间）；**apply 里每次注册都是可逆副作用**，返回销毁器——插件卸载/热重载时一切自动撤除。

dsh-memory 的配置设计值得一抄：

- **注入上下文的预算是必填项**，没有默认值——「往模型上下文里放多少东西」必须由部署显式声明，插件不偷偷决定；
- **全局作用域默认开启**，全局预算默认继承项目预算——一次显式声明同时治理两个作用域，要收紧再单独覆盖；
- **非法配置在加载期就失败**，绝不静默回退。

### 5.2 它挂了哪三个钩子（= 三类扩展点）

一个插件能做出的「模型可见」贡献基本就这三类，dsh-memory 一件不落：

```
              ┌─────────────── DSH 引擎（本身也是插件拼出来的） ───────────────┐
              │   systemPrompt 服务      tools 注册表     agent 循环   会话日志 │
              └────▲───────────────────────▲─────────────────▲───────────▲────┘
   扩展点①        │ section(order 110)     │                 │           │
   常驻策略文本 ───┤                       │                 │           │
                   │   扩展点②             │                 │           │
   模型可调用的 ───┼───────────────────────┘                 │           │
   工具(5 个)      │        工具 schema 自动进系统提示          │           │
                   │                       扩展点③           │           │
   按步拦截注入 ───┼───────────────────────────────────────────┘           │
   (第一步注入索引) │                                  带来源标记的持久消息     │
                   └───────────────────────────────────────────────────────┘
```

**扩展点①：提示词段——给 agent 的常驻指令。**

- 每次模型请求前，引擎把所有段按 order 升序拼成系统提示；段文本是**每次求值**的函数，返回空串则本段整体消失。
- dsh-memory 注册了记忆策略段（order=110，排在人设之后、各工具用法说明之前），并在求值函数里做条件判断：子 agent 会话、无标准工作目录的会话返回空串——**一个段自己决定自己何时出现**。
- 工具注册表也会自动把工具 schema 挂成段，所以「工具 + 用法说明」天然成对出现。

**扩展点②：工具——模型可调用的能力。**

- 定义 = 名字 + 模型可见的描述 + 参数 schema + 输出 schema/渲染 + 执行函数；参数校验由框架在执行前完成。
- 执行函数拿到的上下文里有发起调用的 agent（由此取到会话工作目录和会话 id）和取消信号。
- **工具返回规范化的 JSON 值而非内容块**——渲染是纯投影，同一个值既给模型看，也给界面重放用。
- 调用与结果都作为事件写进会话日志——「模型可见的东西必须可从日志重建」是 DSH 的硬原则，工具结果也不例外。

**扩展点③：agent 事件——按步拦截对话循环。**

- 每个处理步、发模型请求之前，引擎跑一遍 pre-step 瀑布：监听器可以**修改这一步真正进入模型的消息列表**，也可以整体否决这一步。
- dsh-memory 的写法是标准的「先委托后加工」：先调 next() 拿到下游的决策，确认这是第一步且决策是放行，再把两条索引消息插到首批用户消息后面，返回修改后的决策。
- 通用守则：改写下游决策时保留其余声明字段（用展开写法 `{ ...decision, messages }`），别只挑自己认识的字段重建。

### 5.3 插件怎么被装进一个运行形态

DSH 的组合是分层 patch：**官方 bundle（基础层 / GUI 层 / 无头层…）→ 部署 profile 的补丁层 → 用户主目录层 → 命令行 overlay**，逐层叠加出最终的插件树。往一个部署里加插件，就是 profile 补丁文件里写一段插入：

```yaml
- insert:
    - id: dsh-memory
      name: '@deepseek-ai/dsh-memory'
      config:
        maxIndexBytes: 25600
```

dsh-memory 本身是**纯 opt-in**：所有官方 bundle 都不含它，谁要谁挂载——「改引擎」和「带插件」是两码事，这是 DSH 扩展性的基本盘。挂载后可以用 dump-config 命令查看最终插件树来验证。

### 5.4 值得抄的设计取舍（选择 → 理由 → 代价）

**① 直连宿主文件系统，不走可替换的 fs 能力。** 记忆必须「在哪台机器跑就在哪台机器」，无论部署形态怎么变（本地、远程沙箱、容器）。代价有二：绕开了沙箱与可替换性，于是工具内部自建信任边界（文件名单段校验，杜绝路径逃逸）；同时通用文件工具被沙箱挡在记忆目录外，反而形成「记忆工具是唯一写通道」的干净局面。**绕过通用能力时，必须自己补上等价的边界**——这条对所有插件通用。

**② 顶层会话专属，且在每个入口各自把关。** 「只有顶层会话有记忆」这条规则同时落在三处：提示词段返回空、注入跳过、工具报错。教训：**规则不能只挡一个入口**——schema 里省掉参数挡不住直接调用，判定必须落在真正做决定的那个操作里。

**③ 注入 = 带来源标记的持久会话事件。** 把一次性注入做成日志事件，换来三样东西：恢复会话可重放（模型历史从日志派生）、「每作用域至多一次」可查重强制、外加一个伴生校验插件在每次加载/追加时检查结构不变量（框架完整、来源标记齐全、每作用域至多一条）。**凡是模型可见的注入都该走这条路，而不是每次请求现拼**——后者既不可回放，也破坏缓存。

**④ fail loud 与优雅跳过各就各位。** 配置非法、参数非法、越权调用（子 agent）、作用域未启用——一律响亮报错；唯独会话启动时读索引的瞬时失败选择跳过该次注入（工具被真正调用时仍会报出真实错误）。分界线：**能归因到具体调用的错误就地报；属于环境抖动的，延迟到真正需要时再报**。

**⑤ 注册皆可逆 + 成本文档化。** 插件销毁后工具、提示段、监听器必须全部消失（有专门测试验证）；「模型体验」——模型看到什么、每请求的 token 成本、对 KV cache 前缀稳定性的影响——写进包文档。注入型插件直接影响缓存复用，这是新手最容易漏记的一笔账。

### 5.5 写第一个插件的检查清单

1. 先想清楚贡献物落在哪个注册表：常驻指令→提示词段；模型可调用的能力→工具；按步改消息→agent 事件；非模型可见的副作用→对应能力/会话事件。
2. 四导出形态，无 default；配置过 schema 校验，非法值加载期失败。
3. 一切注册走 effect 拿销毁器；为「销毁后一切消失」写测试。
4. 注入模型上下文的内容，用带自有来源标记的持久消息，配伴生校验插件。
5. 工具返回规范化 JSON 值；参数校验交给框架，框架表达不了的约束自己查；尊重取消信号。
6. 往上下文里注入的东西，预算由部署显式声明，不藏默认值。
7. 条件性贡献在每个入口各自把关，别指望一处拦截全局生效。
8. 组合进部署走 profile 补丁层，不碰引擎；用 dump-config 验证。
9. 绕过某个通用能力（沙箱、可替换 provider）时，自己补上等价的边界。
10. 文档写清模型体验与已知边界——已知边界不丢人，它是给下一个部署者的地图。

## 6. 预置 FAQ：初学者最可能问的问题

### 使用者组

**Q1：记忆存在哪？我能自己看、改、备份吗？**
全在 agent 所在机器的本地文件系统上：一个可配置的记忆根目录（默认在用户主目录下的固定位置），里面每个项目一个子目录，外加一个全局目录。全是纯文本 Markdown，随时可以打开看、手动编辑、打包备份——机制每个会话读的都是文件当下的内容，你的手动改动下次会话直接生效。

**Q2：记忆是自动记的吗？还是每次都得我说「记住这个」？**
默认自动：agent 按内置策略自己判断什么值得记（用户偏好、纠正反馈、项目约束……）。你也可以显式要求，显式指令永远优先。反过来它也会自律——仓库里已有的信息、只对当前对话有意义的细节，它不记；你硬要它记这类内容时，它会追问「非显而易见的点是什么」，然后只存那个点。

**Q3：什么不该进记忆？**
三类：① 仓库本身已记录的（代码、修复历史、项目说明文件）——从仓库读比从记忆读可靠；② 只对当前对话有意义的临时细节；③ 说不清「为什么值得记」的内容。

**Q4：新会话是怎么「想起来」的？是把所有记忆全塞进上下文吗？**
不是。只有索引在会话开始时注入一次，且有行数/字节预算；每条记忆的正文要等 agent 判断「与当前任务相关」后才单独读取。两级结构 = 极小的固定成本 + 按需展开。

**Q5：为什么要有索引？直接把记忆文件都注入不行吗？**
记忆会越积越多，全量注入很快撑爆上下文，而且大部分与当前任务无关。索引把成本压成「每条记忆一行」，用最小占位换「知道有什么」；正文成本只花在被判断相关的那几条上。

**Q6：索引太大了会怎样？**
双重预算（默认 200 行 + 部署声明的字节上限，常见 25 KB）整行截断，并提示 agent 读全文、把索引精简回去；往索引写超预算内容时也会收到警告。「一行一钩子、细节进正文」的索引治理是使用方的长期功课。

**Q7：全局和项目拿不准放哪边怎么办？**
记项目。判断题是「换个不相关项目还有用吗」，但拿不准时默认项目侧：记窄了只是别的项目召回不到（局部损失），记宽了会污染这台机器上所有会话（全局损失）。

**Q8：两边记重了 / 记错边了怎么办？有自动仲裁吗？**
没有自动仲裁。规则教给了 agent：发现项目记忆其实跨项目，就四步搬移到全局；同一事实两边都有，删放错边那份、按判断题留对的；你的显式指令随时可以强推。刻意不做后台自动整理——全局内容会注入所有会话，属于高影响面区域，无人值守写入等于绕过人工把关。

**Q9：记忆过时了、记错了怎么办？**
三层防线：写入时更新优先于新建；召回时注入框架明确告诫「记忆只反映写入当时的情况，用前先验证」；发现被证伪的记忆直接删。记忆的正确性是持续治理出来的，不是一次写入保终身。

**Q10：多个会话同时写记忆，会冲突吗？**
单个文件层面安全：写入是原子操作（临时文件 + 改名），不会出现半个文件。文件内容的并发修改是「后写覆盖先写」，和你同时编辑两份普通文本文件一个语义。索引维护被刻意做成「一次只动一行」，把冲突面压到最小。

**Q11：子 agent（子任务）能用记忆吗？**
不能，这是有意的。子任务跑在隔离目录里，让它们写记忆会产生没人召回的孤儿目录；它们调用记忆工具会直接报错。记忆属于顶层会话。

**Q12：恢复会话、压缩上下文之后，记忆注入还在吗？会重注吗？**
在，且不会重注。注入是写进会话日志的持久事件（带来源标记和内容摘要），恢复会话时随日志重放；插件查日志去重，每个作用域至多注入一次；压缩也不触发重注入。会话中途想看最新记忆，直接让 agent 用 memory_read 读。

**Q13：记忆会上云、会被别的机器共享吗？**
存储完全本地：插件刻意直连宿主机文件系统（而不是走可替换的远端文件能力），保证任何部署形态下记忆都不出本机。需要说明的是：被注入/读取的记忆内容自然会作为模型请求的一部分发往模型服务——这是所有 LLM 记忆机制的固有属性，与存储位置是两回事。

**Q14：记忆和项目里的说明文件（AGENTS.md 那类）有什么区别？**
说明文件是仓库的一部分：进版本库、团队共享、每次会话整体生效，适合「这个项目怎么干」的稳定约定。记忆是 agent 的个人笔记本：不进仓库、按相关性召回、随时增删，适合「从仓库推不出来的事」。策略明确禁止把仓库已记录的内容搬进记忆——两者是分工，不是冗余。

### 插件初学者组

**Q15：一个 DSH 插件最小长什么样？**
四个导出：name（名字）、inject（依赖的服务）、Config（配置 schema）、apply（注册逻辑），没有 default 导出。apply 里做的每次注册都返回销毁器。一个几十行的插件就能给 agent 挂上工具和常驻指令。

**Q16：dsh-memory 一共挂了哪几个钩子？**
三类各一个：提示词段（常驻记忆策略，order 110）、五个工具（memory_*，schema 自动进系统提示）、一个 agent 事件监听（会话第一步注入索引消息）。加上配置与一个伴生的日志校验插件，全部贡献就这些——一套完整的模型可见能力，三个扩展点足够。

**Q17：插件怎么被装进一个运行形态？**
DSH 按「bundle → profile 补丁 → 用户层 → 命令行 overlay」分层组合出插件树。加插件就是 profile 补丁文件里一段 insert（声明插件名和配置），然后用 dump-config 命令验证最终树，引擎代码零改动。dsh-memory 本身就是纯 opt-in：官方 bundle 都不含它，全靠各部署自己挂载。

**Q18：注入为什么做成「持久会话事件」而不是每次请求现拼？**
三个理由：恢复会话时历史从日志派生，持久事件天然可重放；「每个作用域至多一次」靠扫日志查重就能强制；来源标记 + 内容摘要让它可审计（伴生插件会校验结构不变量）。DSH 的硬原则是「模型可见的东西必须可从会话日志重建」——现拼的内容回放不出来，也不利于缓存。

**Q19：它的文件操作为什么不走沙箱/可替换的 fs 能力？**
因为记忆必须在宿主机本地，无论部署形态怎么变（沙箱、远程、容器化）。直连宿主文件系统是刻意豁免；豁免的代价是自建信任边界（文件名严格单段校验，杜绝路径逃逸）。副产品：标准沙箱策略下通用文件工具被挡在记忆目录外，记忆工具成了唯一写通道。**绕过一个通用能力，就要自己补上它原本提供的保证**——通用守则。

**Q20：配置为什么把索引预算设成必填？**
往模型上下文注入多少内容是部署级的成本决策，插件不该替部署做主。必填（且全局预算默认继承项目值）保证「一次显式声明，两个作用域都有上限」。非法配置在加载期直接失败，绝不静默回退到某个默认值。

**Q21：写插件最容易踩的坑是什么？**
按常见程度排：① 忘了注册是可逆的（没走 effect，热重载后残留）；② 条件性贡献只挡了一个入口（schema 里省了参数，直接调用照样进得来）；③ 注入模型上下文的东西没有会话事件兜底（恢复会话就对不上账）；④ 忘了算 token 和 KV cache 的账（每请求固定成本、前缀稳定性）；⑤ 绕过通用能力却不补边界校验。§5.5 的清单逐条防这些。

## 7. 已知边界与取舍（附录）

| 边界 | 现状 | 性质 |
|---|---|---|
| 并发写同一文件 | 后写覆盖先写（写入本身原子，不会出半个文件）；无文件锁 | 与并发编辑普通文件同语义，接受 |
| Windows 工作目录 | 不支持：无提示段、无注入、工具响亮报错 | 有意——目录派生规则未在那类路径上验证，宁可失败不猜 |
| 会话中途索引不重载 | 本会话内改动索引/记忆，已注入部分不刷新 | 有意——一次性注入换缓存前缀稳定；要最新状态用 memory_read |
| 无「接近预算」提醒 | 只有写入超预算后的警告，没有临近提醒 | 已知改进项（补充式提醒，不影响格式） |
| 元信息无格式强制 | frontmatter 缺字段不报错，机制只做加法回填 | 有意——格式纪律交给策略层，与「机制不替 agent 做记忆决策」一致 |
| 无定时项目→全局晋升 | 搬移/去重只由 agent 按规则机会主义执行 | 有意——见 §4.2；升级路径是按需审计而非后台进程 |
| 跨作用域去重无工具强制 | 规则只存在于提示词与注入框架文案，无后台对账 | 有意——同上 |
