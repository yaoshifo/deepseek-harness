# 派发到并行子任务（feishu-bridge）

这个 skill 驱动 `feishu_bridge_subtask` 工具——把每一块工作作为**隔离的原生子 agent 会话**派发，并行运行，再把结果折回本对话。它适合多方向并行调研、需要独立目录、git worktree 隔离、或运行时间较长的工作。子任务**没有用户可见的群**：用户要围观或介入的活走 `/spawn`（attended 群），不用这里。

## 在 plan mode 下：只读探索直接派，执行型派发先请求退出

先按「什么时候不该用子任务」自查：轻量单焦点问题（一两次 read/grep 可答）不该走到这里。如果工作确实需要子任务（多方向调研并行、用户明确要并行派发，或需要独立目录 / worktree 隔离），**不要**偷偷换成不开子任务的轻量委派；那会丢掉用户刚要的隔离和并行。

**只读探索 spawn 直接派。** brief 写明只读回报的多方向调研 spawn，plan-mode 引导文案已授权在 plan mode 内直接派发——结果折回本对话写进计划，不需要先退出 plan mode。

**执行型 spawn（子任务要改文件、建 worktree）是「执行」**，plan mode 会拦住它，必须先过用户的批准门。设计上的通路是 `ExitPlanMode`：

1. 调用 `ExitPlanMode`，带一个具体计划，列出你要派发哪些子任务——每块 `action: spawn` 的 brief、各自做什么，以及你打算怎么综合它们的回报结果。
2. 如果用户**批准**，你就退出 plan mode——然后按下面正常派发。
3. 如果用户**拒绝**，留在 plan mode 等着；不要派发。

`ExitPlanMode` 是一个*请求*——用户可以拒绝，所以你不是在 overriding 他们的 plan-mode 保护，你只是在请求继续。这才是正路；不要靠降级到别的委派机制来绕开 plan mode。

**审批通过后的实施期同样默认并行**：计划里标注独立的组在执行开始时一起派发子任务，串行依赖的组自己按序实施——与全局指令、工具描述是同一条边界。

## 角色：父会话协调，子任务执行

你（父会话）是**协调者 / 审查者 / 综合者**——不是额外的工人。你的活是拆活、派发子任务、收每条子任务回报、对结果做 sanity check、合并成一个答案给用户。

- **不要自己做子任务的活。** 一块能派发就派发，让子任务在它自己的隔离环境里做。只有当子任务真的没法独自推进时（比如需要一个只有你/用户能做的决定）才介入。
- 每个子任务应当是一个**自包含的 vertical slice**，brief 要完整到子任务很少需要回头问你。
- 子任务已经知道自己是被派发的工人——它的人设里注入了「你是一个被派发子任务的子 agent」的 preamble，并告诉它用 `feishu_bridge_subtask` 的 `action: report` 把结果交回来。所以你完全掌控的就是你传的 **brief**，以及可选的 **forked 上下文**（见下面 `fork`）。把精力投在这两者上，而不是微观管理。

## 派发一个子任务

每块独立的工作，各调一次 `feishu_bridge_subtask`：

```
action: spawn
message: "迁移 project A 里的 schema"
dir: /abs/path/to/project-a
worktree: on
```

```
action: spawn
message: "更新 project B 里所有调用方"
dir: /abs/path/to/project-b
worktree: on
```

- `dir` — 子任务的工作目录（默认是本会话目录）。
- `worktree` — **默认就带 `on`。** 它让子任务跑在专属的 git worktree + branch 里，这样并行子任务改同一个仓库时永远不会互相覆盖。养成每次 spawn 都带上的习惯。只在隔离没意义时才降到 `off`：只读/调查任务、非 git 目录、或不同的仓库。（省略时是 `auto`——仅当目录是同一个仓库时才隔离——但宁可显式带 `on`，别依赖自动检测。）
- `fork` — 把你完整的对话上下文复制进子任务（session fork），而不是从全新上下文开始。当子任务**依赖当前讨论**——探索发现、设计决策、用户在本会话给的额外要求——**就上 `fork: true`**：它直接把你的上下文交给子任务，省得你把这一切重写进 brief，也避免手写 brief 留下的缺口。代价：它复制整个 transcript，更费 token，且需要一个已经开过的对话来 fork。当任务自包含、一行 brief 就说清时，默认的全新上下文就够了。可与 worktree、`dir` 组合——跨目录 fork 可用（上下文从持久化日志复制，与目录无关）。
- `message` 是子任务描述（成为子 agent 的首条消息）。

调用会返回子任务的标签和 session key——**记下这个 key**，跟进（send）或打断（interrupt）时要用的就是它。

你不用（也不能）传当前会话的身份参数——工具按你本人自动路由到你所属的项目和会话。

## 什么时候不该用子任务

**轻量单焦点问题不开子任务**——一两次 read/grep 就能回答的，直接自己做：子任务有真实副作用（独立 agent 会话、汇报链路），撑不起这点收益。判「单焦点」看答案要覆盖几个子系统/方向，不看几条命令能扫完——大合并审查、发布审查、全仓库扫描、横切审计哪怕几条命令能列个概要，也不是单焦点。**多方向调研默认并行派发**：大合并/发布审查、全仓库扫描、横切审计、用户点名了几个方向的调研——每个方向预期要读多个文件、多轮探查——拆 2–5 路 spawn 一起派发，各自只读回报，由你综合；无群后台形态成本可控，不要因为「同一个项目」或「只读」就放弃拆分。子任务独有能力覆盖的工作：跨目录、worktree 隔离、长任务。用户明确要围观/介入的，走 `/spawn`（attended 群）。

## 投递契约：默认逐个唤醒，gather 阻塞等齐

spawn 立即返回，子任务独立并行跑。默认**没有 fan-in 屏障**：每个子任务完成时其结果作为一条回报消息注入回本对话、唤醒你——N 个子任务 N 次唤醒，你逐条响应（想立刻消化快结果、或任务时长参差时用这个模式）。记住你派发了几个，等全部回报后自己合并。

**批量任务用 gather：阻塞等齐，同一回合综合。** 派发完所有要批量的子任务后调 `gather`——工具调用会**挂起**直到所有在途子任务回报（或默认 20 分钟超时），`[子任务汇总]` 作为 gather 的工具结果直接回到本轮：

```
action: spawn  ×3   （A / B / C 三块工作，各自 spawn）
action: gather      # 阻塞——等待期间子任务活动实时滚动在你的进度卡上
→ 收齐后汇总作为工具结果回到本轮 → 你在同一回合里审查、综合、回复用户。
```

- gather 期间你这轮保持「执行中」：每个子任务的工具活动实时流入你的进度卡，用户全程可见谁在跑、跑到哪。
- **先把要批量的子任务全部派发完**再 gather（推荐顺序，最可预测）。gather 之后派发的子任务也会被**自动纳入等待**。
- **兜底超时**：某个子任务卡住或崩溃没回报时，超时用已到的结果返回并标注缺失者（默认 20 分钟）——不会永远阻塞。想立刻对第一个结果行动就别用 gather。
- 等待期用户发来的消息会排队，gather 返回后你先处理。
- 内存等待：gather 中途进程重启会丢等待，后续 report 正常逐条唤醒你。需要的话用 `gather` 重新架。
- 你自己若是被派发的子任务（native 链），`gather` 不可用：你的子任务回报逐条经原生 inbox 唤醒你。

## 跟进一个运行中的子任务

子任务**在回报后仍存活**——你可以再找它。如果某条回报结果太简短没法行动（比如子任务说「发了报告」但你从没看到内容），就问它要细节，别猜：

```
action: send
child: <spawn 返回的 session key>
message: "把完整报告内容贴出来"
```

- `child` 是 spawn 结果里的 session key，它也附加在你收到的每条回报消息上，你可以从唤醒消息里复制。
- `send` 是**非阻塞**的，跟 `spawn` 一样：消息**排队**到子任务当前轮结束后作为它的下一轮送达，回复作为另一条回报消息折回、再次唤醒你。发送后结束你这轮；不要等。
- 你可以反复跟进——每轮用一个新答案唤醒你——直到你拿到足够综合的内容。

**只在还需要 PULL 信息时才 `send`。** 当一条回报已经够你行动，直接综合并回复用户——**不要** send 子任务一个确认、「谢谢」、「你做完了」、或「请停止」。子任务不需要被告知停止；保持沉默就结束了交换。一个不问任何东西的 send 只会烧一个来回、还可能 ping-pong。每次 send 都应包含一个你还看不到答案的真问题。

## 打断一个跑偏的子任务

子任务的当前轮跑偏（明显死循环、方向错了）时，可以打断它的当前轮而不销毁会话：

```
action: interrupt
child: <spawn 返回的 session key>
```

打断只停当前轮；之后仍可 `send` 继续问它，或让它带着修正指令重跑。

## 递归

子任务 agent 自己也能用 `feishu_bridge_subtask` 进一步派发（child → grandchild → …），到深度上限为止；结果逐层折回（native 子链经原生 report 通路）。如果碰到深度上限，工具会报错，让子 agent 自己直接做。

## 清理

子任务没有群可拆。worktree 的回收走用户在父会话发 `/done`——它递归清理所有后代（含 native 子任务）的 worktree（干净 worktree 自动删除；有改动的保留并给出摘要，不会丢未提交的内容），并打断仍在跑的 native 后代。

## 典型流程

```
用户（明确）：把这几块拆开并行跑：
  A. <dir A 里的任务>
  B. <dir B 里的任务，依赖我们刚讨论的设计>

你（协调者——派发，别自己做 A/B）：
  feishu_bridge_subtask: action=spawn, message=<task A 自包含 brief>, dir=/path/A, worktree=on
  feishu_bridge_subtask: action=spawn, message=<task B brief>, fork=true   # B 需要我们的讨论，fork 把上下文带给它
  feishu_bridge_subtask: action=gather      # 阻塞等两者回报；期间子任务活动实时滚动在进度卡上
  → 收齐后 [子任务汇总] 作为工具结果回到本轮 → 同一回合里审查、综合、回复用户。

（没有 gather 的话，A/B 各自的回报会作为独立唤醒逐条到达，你逐条响应。）
```
