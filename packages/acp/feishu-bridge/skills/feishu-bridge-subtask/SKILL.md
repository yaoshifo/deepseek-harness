# 派发到并行子任务群（feishu-bridge）

这个 skill 驱动 `feishu_bridge_subtask` 工具——把每一块工作作为**独立群聊 + 隔离 agent 会话**派发，并行运行，再把结果折回本对话。它适合需要独立目录、git worktree 隔离、在专门群里让用户可见/可介入、或运行时间较长的工作。

## 在 plan mode 下：请求退出，不要降级

先按「什么时候不该用子任务群」自查：同项目内的只读调研不该走到这里——那种用 `subagent` 工具并行派发，结果直接折回本对话。如果工作确实需要子任务群（用户明确要群，或需要独立目录 / worktree 隔离 / 专门群），**不要**偷偷替换成进程内的一次性 subagent 委派；那会丢掉用户刚要的专门飞书群、独立目录和 worktree 隔离。

spawn 有真实副作用（建群、起会话），plan mode 会拦住它。设计上的绕法是 `ExitPlanMode`：

1. 调用 `ExitPlanMode`，带一个具体计划，列出你要派发哪些群——每块 `action: spawn` 的 brief、各自做什么，以及你打算怎么综合它们的回报结果。
2. 如果用户**批准**，你就退出 plan mode——然后按下面正常派发。
3. 如果用户**拒绝**，留在 plan mode 等着；不要派发。

`ExitPlanMode` 是一个*请求*——用户可以拒绝，所以你不是在 overriding 他们的 plan-mode 保护，你只是在请求继续。这才是正路；不要靠降级到别的委派机制来绕开 plan mode。

## 角色：父群协调，子群执行

你（父群）是**协调者 / 审查者 / 综合者**——不是额外的工人。你的活是拆活、派发子任务、收每条子任务回报、对结果做 sanity check、合并成一个答案给用户。

- **不要自己做子任务的活。** 一块能派发就派发，让子群在它自己的隔离环境里做。只有当子群真的没法独自推进时（比如需要一个只有你/用户能做的决定）才介入。
- 每个子任务应当是一个**自包含的 vertical slice**，brief 要完整到子群很少需要回头问你。
- 子群已经知道自己是被派发的工人——平台会在它那边注入一段「你是一个被派发子任务的子 agent」的 preamble，并告诉它用 `feishu_bridge_subtask` 的 `action: report` 把结果交回来。所以你完全掌控的就是你传的 **brief**，以及可选的 **forked 上下文**（见下面 `fork`）。把精力投在这两者上，而不是微观管理。

## 派发一个子任务

每块独立的工作，各调一次 `feishu_bridge_subtask`：

```
action: spawn
message: "迁移 project A 里的 schema"
dir: /abs/path/to/project-a
worktree: on
```

```
action: spawn
message: "更新 project B 里所有调用方"
dir: /abs/path/to/project-b
worktree: on
```

- `dir` — 子任务的工作目录（默认是本群目录）。
- `worktree` — **默认就带 `on`。** 它让子任务跑在专属的 git worktree + branch 里，这样并行子群改同一个仓库时永远不会互相覆盖。养成每次 spawn 都带上的习惯。只在隔离没意义时才降到 `off`：只读/调查任务、非 git 目录、或不同的仓库。（省略时是 `auto`——仅当目录是同一个仓库时才隔离——但宁可显式带 `on`，别依赖自动检测。）
- `fork` — 把你完整的对话上下文复制进子任务（session fork），而不是从全新上下文开始。当子任务**依赖当前讨论**——探索发现、设计决策、用户在本群给的额外要求——**就上 `fork: true`**：它直接把你的上下文交给子群，省得你把这一切重写进 brief，也避免手写 brief 留下的缺口。代价：它复制整个 transcript，更费 token，且需要一个已经开过的对话来 fork。当任务自包含、一行 brief 就说清时，默认的全新上下文就够了。可与 worktree 组合。**跨目录时 fork 不可用**：fork 需要在子任务自己的目录下找到父会话的 transcript，父子目录不同就找不到——spawn 会在建群前直接报错拒绝（不会降级、不会建群）。`dir` 指向不同于本群的目录时，去掉 `fork`，用全新上下文 + 把依赖写进 brief。
- `message` 是子任务描述（成为子 agent 的首条消息和群名）。

调用会返回子群的名称和 session key——**记下这个 key**，跟进（send）时要用的就是它。

你不用（也不能）传当前会话的身份参数——工具按你本人自动路由到你所属的项目和会话。

## 什么时候不该用子任务群

**同一个项目内的只读调研 / 勘察不开子任务群。** 子任务群有真实副作用（建群、独立会话、汇报链路），而这类工作的结果要折回本对话综合——用进程内 `subagent` 工具在同一条消息里并行派发几个只读调研任务即可，轻得多，也不用麻烦用户清理群。子任务群留给它独有能力覆盖的工作：跨目录、worktree 隔离、需要用户在专门群里围观或介入的长任务。

## 非阻塞——不要等

spawn 立即返回。**派发完后正常结束当前这轮。** 每个子任务在各自群里独立跑。子任务完成时，它的结果作为一条子任务回报消息注入回本对话，唤醒你去综合。

默认**没有 fan-in 屏障**：每个子任务给你一次唤醒，各自独立到达——所以 N 个子群意味着 N 次唤醒，你逐条响应。记住你派发了几个，等全部回报后自己合并。

### 可选：用 gather 批量唤醒（全部回报后统一回复一次）

当你派发了多个独立子任务、想**在同一条回复里一起综合**，而不是逐条 trickle 进来时反应，就在**派发完所有要批量的子群后**架一个 gather 屏障，然后结束这轮：

```
action: spawn  ×3   （A / B / C 三块工作，各自 spawn）
action: gather
→ 回复 "已派发 A/B/C；等它们都回报后我把三者合并。"
→ 结束这轮。
```

`gather` 快照你**当前在途（已派发、尚未回报）的子群**，并在本会话上装一个内存屏障。每个子群的 report 仍作为回报卡片投递（立即可见）但**不**唤醒你；你只被唤醒**恰好一次**——带着一条所有子群的 `[子任务汇总]` 汇总——在最后一个预期子群回报时。

- **先把要批量的子群全部派发完**，再 `gather`，再结束这轮（推荐顺序，最可预测）。`gather` 之后派发的子群也会被**自动纳入屏障等待**——它们的 report 同样参与倒计时，gather 会等全部（含后续 spawn 的）子群回报才唤醒。
- **兜底超时**：如果某个子群卡住或崩溃没回报，屏障会用已到的结果唤醒你，并标注缺失的子群名（默认 20 分钟）。所以你永远不会永远阻塞——但若你想立刻对第一个结果行动，就别用 `gather`。
- **忘了 `gather`？** 没事——你就是拿到默认的每子群一次唤醒。`gather` 纯属 opt-in。
- 内存屏障：gather 中途进程重启会丢屏障，后续 report 正常唤醒你。需要的话用 `gather` 重新架。

## 跟进一个运行中的子任务

子任务群**在回报后仍存活**——你可以再找它。如果某条回报结果太简短没法行动（比如子任务说「发了报告」但你从没看到内容），就问它要细节，别猜：

```
action: send
child: <spawn 返回的 session key>
message: "把完整报告内容贴出来"
```

- `child` 是 spawn 结果里的 session key，它也附加在你收到的每条回报消息上，你可以从唤醒消息里复制。
- `send` 是**非阻塞**的，跟 `spawn` 一样：子任务在它自己群里回答，回复作为另一条回报消息折回、再次唤醒你。发送后结束你这轮；不要等。
- 你可以反复跟进——每轮用一个新答案唤醒你——直到你拿到足够综合的内容。

**只在还需要 PULL 信息时才 `send`。** 当一条回报已经够你行动，直接综合并回复用户——**不要** send 子任务一个确认、「谢谢」、「你做完了」、或「请停止」。子任务不需要被告知停止；保持沉默就结束了交换。一个不问任何东西的 send 只会烧一个来回、还可能 ping-pong。每次 send 都应包含一个你还看不到答案的真问题。

## 递归

子任务 agent 自己也能用 `feishu_bridge_subtask` 进一步派发（child → grandchild → …），到深度上限为止；结果逐层折回。如果碰到深度上限，工具会报错，让子 agent 自己直接做。

## 清理

子任务群在回报后仍存活（方便用户检视/继续）。要拆掉它们，用户在父群发 `/done`——它递归清理所有后代群及其 worktree（干净 worktree 自动删除；有改动的保留并给出摘要，不会丢未提交的内容）。

## 典型流程

```
用户（明确）：把这几块拆到独立群并行跑：
  A. <dir A 里的任务>
  B. <dir B 里的任务，依赖我们刚讨论的设计>

你（协调者——派发，别自己做 A/B）：
  feishu_bridge_subtask: action=spawn, message=<task A 自包含 brief>, dir=/path/A, worktree=on
  feishu_bridge_subtask: action=spawn, message=<task B brief>, fork=true   # B 跟本群同目录、且需要我们的讨论（跨目录带 fork 会被拒）
  feishu_bridge_subtask: action=gather                                     # 批量：两者都回报后唤醒一次
  → 回复 "已把 A 和 B 派发到独立群；等它们回报我来审查并合并结果。"
  → 结束这轮。

稍后：一条 "[子任务汇总]" 消息带着两者结果到达 → 你对各自做 sanity check，
   然后综合并回复合并后的结果。（没有 gather 的话，你会拿到两条独立的回报唤醒。）
```
