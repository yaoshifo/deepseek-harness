# 原型（Prototype）

原型是**用来回答一个问题的丢弃物**。问题决定形状——先把要回答的问题写清楚，再动手。

## 选分支

- 「这个逻辑/状态模型对不对？」→ **逻辑原型**：单文件 HTML，按钮驱动状态机，把纸面上难推理的场景点出来看。要回答的问题写在页面顶部可见处（不是注释）。交付走 html skill 直投聊天——非开发者也能自己点着看。
- 「这该长什么样？」→ **UI 原型**（仅 web 项目适用）：一条路由上生成多个**激进不同**的变体，浮动条切换，用户翻着挑或从各变体各偷一点。

问题真分不清且用户不在时，默认选更贴近上下文的分支（后端模块→逻辑；页面/组件→UI），并在页首声明这个假设。

## 六条护栏

1. **从第一天起标记为丢弃物**。命名让扫一眼就知道是原型不是产品（`prototype-` 前缀），放在贴近使用处但明确隔离的位置；不发明新的顶层目录结构。
2. **一条命令能跑**。逻辑原型是双击即开的单文件 HTML；UI 原型是任务 runner 里的一条命令。启动不需要思考。
3. **默认无持久化**。状态在内存里——持久化恰是原型要验证的东西，不是它该依赖的；确需数据库就上带「PROTOTYPE, wipe me」名字的 scratch 库或本地文件。
4. **跳过打磨**。无测试、无超出「能跑」的错误处理、无抽象。目的是快速学到东西，不是写好代码。
5. **每个动作后摆出全量状态**（逻辑）或每次变体切换后重渲染全景（UI），让用户看见什么变了。
6. **做完即收**。把验证过的决定**折回正式设计**——grill 的决定汇总、或 tdd 的实现起点——然后删掉原型或明确标记归档。**原型代码绝不迁移进产品，只迁移结论。**

## 边界

- 与 grill 的衔接：grill 协议第 3 条（谈不出来的问题）指名本 skill；实验结果回来用一句话回答，继续访谈流程。
- 验证通过转正式实现走 `tdd`。
- 排查「为什么坏了」不是原型的事，走 `diagnose`。
