# dsh-feishu-bridge

English | [中文](README.zh.md)

## Summary

Run Feishu group-chat bots from one long-lived dsh process: each configured project gets an engine plus a Feishu long-connection platform, and chats drive real agent sessions whose turns render as live progress cards, approval and question cards, and terminal completion cards. Delegate parallel work through `feishu_bridge_subtask` children that run as native continuable sessions and settle back into the parent chat, schedule unattended runs with cron, and call Feishu open APIs through the `lark-cli` tool. Each project is one configuration entry; the slash-command family (`/reload`, `/spawn`, `/dir`, `/skills`, `/context`, …), i18n, and per-project tool visibility come with the layer, while per-machine policy stays in the profile.

cc-connect's orchestration capability (engine + Feishu platform) migrated into dsh as a single plugin: one long-lived dsh process assembles, per configured project, an Engine plus a Feishu WS platform (official node-sdk long connection, D5); agent sessions are created natively through `ctx.agents`, with no bridge protocol left. The migration plan, milestones, and decision records live in [docs/MIGRATION.md](docs/MIGRATION.md); the 61-item feature comparison in [docs/FEATURE-PARITY.md](docs/FEATURE-PARITY.md); deployment and configuration mapping in [docs/OPERATIONS.md](docs/OPERATIONS.md).

Plugin structure:

| Directory | Contents |
|---|---|
| `src/engine/` | faithful port of Go `core/`: the event state machine, sessions, commands, cron, relay, monitor, i18n, attachment staging |
| `src/feishu/` | port of Go `platform/feishu/`: WS, API client, cards, progress cards, chat management, tags, avatars, media, quoted-message fetching |
| `src/agent-dsh/` | Agent interface → `ctx.agents` adapter (D1/D3: setup hooks, provider routing, approval/question/plan wiring) |
| `src/tools/` | the `feishu_bridge_subtask / cron / relay / lark / send` tool families (D4: caller-agent routing, no env needed; the `feishu_bridge_chatroom` family registers from the sibling chatroom plugin, `@deepseek-ai/dsh-feishu-bridge-chatroom`); the lark tool registers as `lark-cli` — named verbatim after the official CLI so every command reference in lark-cli's embedded skills maps literally to a tool call, and its description routes domain tasks through `skills list` / `skills read` |
| `skills/` | bridge skills (`feishu-bridge-` prefix) plus the deployment's working-style skills (`tdd`, `skillify`), auto-mounted as an isolated skill provider by `apply()` — no `customSkillDirs` wiring needed |

Native subtasks (de-baggage B4): the profile's `dsh-base` bundle mounts `SubagentRuntime` (with `settlementNotice: 'external'`, overridden via this bundle's patch) plus the in-process spawn/fork providers, so unattended `feishu_bridge_subtask` spawns run as native continuable child sessions — no Feishu group — with lineage, depth, and cold resume owned by the native runtime; the engine keeps only the parentage record (persisted in the project state, surviving restarts) and the worktree it created. The bundle patch also disables `tool-subagent-report`: its `report` tool delivers straight into the runtime parent inbox, a channel the engine cannot observe, so a child using it double-delivers (runtime splice plus engine settlement, 2026-08-27 oc_56801302); `feishu_bridge_subtask` action=report is the single reporting surface (the subagents service's reportFrom path stays for native-parent delivery). Settlement reaches the engine through the `subagent/end` listener: a child that never explicitly reported still delivers its final assistant output through the same card + `[子任务完成]` wake as the group path, and a follow-up's answer re-arms that delivery. Every machine wake (child report, gather summary, chatroom moderator wake, follow-up injection) routes through `deliverMachineMessage`: a busy parent turn receives it mid-turn via the agent-session steer primitive (several wakes batch into one step) instead of entering the platform message queue, whose queued-notice reply, in-memory storage, and length cap are human-conversation semantics; an idle parent keeps the synthetic-message path so the wake runs with the full turn machinery. A daemon restart kills in-flight child epochs silently, so `recoverInterruptedNativeChildren` runs at platforms-ready: every unreported child without a live agent is settled and its parent chat receives a red warning card plus the notice (resumable via `send`, which re-arms the record) — the subtask counterpart of the chatroom plugin's barrier recovery; a child that IS live (an HMR rebuild that kept the runtime alive) is left untouched. The settlement text carries the terminal outcome — a non-completed stop reason prefixes failure semantics (error / max-tokens / refusal / aborted, plus the provider diagnostic and a no-closing-output notice when the epoch left none), so failed work never reports as finished. `gather` is the synchronous delivery contract: the call blocks until every in-flight child reports or the gather timeout (default 20 minutes) returns a partial summary naming the missing, and the summary lands as the call's own result in the still-open parent turn — child tool activity streams on its live card while the call is in flight, and an aborted wait (user stop) settles the tool call with an abort notice — a parked turn must be able to end, or the agent can never quiesce and its session leaks live in the runtime registry — while banked reports still arrive via the async wake. The expected set holds only children that can settle the barrier (subtask-depth sessions and native children); chatroom role groups hanging off the hub are excluded — their replies settle through the chatroom plugin's relay — and a parent with no gatherable child fails fast instead of arming a timeout-bound barrier. `send` queues behind the child's running turn (the deliberate deviation from Go's busy-reject) or, with `delivery: 'steer'`, admits the follow-up at the running child's nearest step boundary (native children only; attended groups reject steer loudly), `interrupt` stops the current turn without disposing the child, and `/done` / chatroom end drain native descendants (interrupt + clean-worktree recycle). Mounting another `dsh-subagent` row would collide with `dsh-base`'s registration (DUPLICATE_PROVIDER fails the whole plugin tree) — the runtime and the spawn/fork providers belong to base; this bridge only overlays the delivery mode via its bundle patch. The generic `subagent` / `subagent_fork` tools stay disabled in this composition (their children are invisible to the engine), so the same patch also overrides the plan-mode section's delegation sentence — base's tool-neutral "background subagent delegations" wording would name those disabled tools, and the override dispatches `feishu_bridge_subtask` spawns instead; every other paragraph stays verbatim from base, with a lockstep spec (`tests/bundle-patch.spec.ts`) failing until the sentence is re-adapted whenever base's section evolves ([Agent Note](../../../.agents/notes/implemented/architecture/2026-09-01-feishu-bridge-plan-mode-guidance-in-bundle-patch.md)). The same patch owns the rest of the deployment-class rows the profiles used to hand-copy — the goal-family / workflow / ralph / second-editor disables, the `tool-ask-user` and `dsh-memory` mounts, the harness-identity suppression, and the CLAUDE.md instruction candidates — while per-machine policy (sandbox and permission presets, model route, MCP and lsp mounts, credentials) stays in the profile ([Agent Note](../../../.agents/notes/implemented/architecture/2026-09-01-feishu-bridge-deployment-class-config-in-bundle-patch.md)). A drained worktree whose only dirty cause is commits already contained in its containment target — as ancestors or patch-equivalent after a rebase — is removed automatically instead of being kept; the target defaults to the branch HEAD was on when the worktree was created (per-repo, zero config), with `spawn.integrateBranch` as a global override. Uncommitted changes and unmerged commits always keep the worktree (the group path keeps them for the per-child Keep/Remove card); a detached or unknown creation-time base branch leaves auto-removal off for that worktree. Attended groups (`/spawn`, monitor children, chatroom pre-spawned assistants) keep the group path unchanged, and group-path children gained the matching failure notices: an error-reasoned turn auto-reports with the failure and its own partial streamed text (never a stale earlier reply), a mid-turn process exit reports the partial output with an interruption prefix, and terminal cleanup paths (stall kill, hard turn cap, dead-agent send failure) deliver the synthetic timeout notice so the parent never waits forever. `features.subtaskQuiet: true` suppresses the settlement card for unattended native subtasks — the result reaches the parent agent context through the wake only, matching the generic `subagent` tool's silent return; attended group children and monitor chats keep their cards either way. Unreported native children stay visible while they run: a spawning turn shows a `subtasks_running_hint` line beside the stop button, and every settled card title appends `· N 个子任务在途` (plus the body hint and the same line on the ✅ completion push), the count recomputed from the persisted records at each render — the header itself stays terminal, because the parent turn really did end. When a turn settles with children still running (the no-gather escape path), the background-subtask live panel posts a standalone card that PATCHes in place every `features.subtaskLivePanelIntervalMs` (default 15s): the header follows the tool-progress card's running composition — yellow template, spinner icon when the platform has one, and a wall-clock last-activity `HH:MM:SS` that advances on every tick and freezes once every child stalls; any child silent past `features.subtaskLivePanelStallMs` (default 120s) flips the template orange with a stalled count. One row per pending child — label, tool-call count, absolute last-activity clock — and a Stop-all button interrupting every running child; the card finalizes to a done (or drained, on `/done`) terminal once the set settles. Its data comes from the adapter's subagent activity recorder, fed by every delegated child's durable events independently of the ancestor projection (which dies with the parent turn's detach — the projection only serves a live turn's card); gather turns never post a panel, since their live card already streams child activity. A spawned group's avatar background is a five-color lifecycle signal: yellow while no plan is approved (discussion, direct work, never-planning runs alike), blue while an ExitPlanMode card is parked, green once approved, red when the user must step in (a pending question/permission card, an errored turn, a stall timeout), gray after `/done`; a done-marked group ignores later engine repaints (a stop-settled ask, turn-end baselines) until `/undone` or the next message reactivates the avatar; same-color transitions are deduplicated so each Feishu avatar-update system message marks a real state change, and chatroom families / branded hubs keep name-hashed colors outside the signal ([Agent Note](../../../.agents/notes/implemented/feature/2026-08-26-feishu-bridge-lifecycle-phase-avatar.md)).
Model-visible surface: inbound messages (with reply-chain prefixes and staged-attachment path notes) enter the prompt; outbound goes through the card system (progress cards, completion cards, approval cards). A turn that ends with an error reason (for example a provider content-moderation rejection) finalizes the progress card as 执行失败 with the error text replacing the live-narration section, records the error as the turn's reply, and sends it as a plain message when no preview card is active; interim narration between tool calls never stands in as the final answer. Every turn exit renders a terminal card: user and engine stops land the ⏹ stopped card whether the event loop drains the stop arm, a channel close racing the stop, or a plugin reload; stall retries retire the stalled card as failed, abnormal agent exits fail the card, and the hard-cap force cleanup fails the running card the same way, its reset notice also marking parked question/approval cards invalid; late Running PATCHes after a stopped render are dropped. Engine stop additionally fires the state's stop signal, so an ask parked on card delivery settles cancelled instead of hanging on a stopped platform — the parked tool call can never outlive the engine and leak the session live in the persistence coordinator; a cron run's scheduler timeout fires the same signal on its `#cron:` slot, so an unattended run whose turn parked on an ask still ends when the job times out (the runtime turn-cancel alone cannot settle an engine-side ask wait). Ask and permission cards on a cron new-per-run slot stamp the reply context's bare session key into their callback values, so their click dispatches arrive addressed by the bare key: ask routing falls back to the newest `#cron:` slot with a parked ask for card actions only — free text stays on the exact key, since an ordinary chat message must not answer a parked cron ask (2026-08-31 cron-fbe6d268: the click fell through as plain `askq:` text and queued behind the very turn it was meant to settle). An ask parking the turn detaches the live preview as a blue 等待中 card instead of a premature 执行完成 (the pre-ask segment is delivered, the turn itself still waits); settling the ask PATCHes that card's header to the outcome — 已批准/已拒绝/已回答/已取消, keeping its export/reply buttons while the stop button moves to the post-decision card — so no parked card keeps claiming 等待中 after the user answered, and the wall time spent parked is exempt from the hard turn cap: the cap is evaluated on event arrival, so for a parked ask the first arriving event is the user's answer, which must not be destroyed by the very check it wakes (2026-08-28 oc_9d385: an overnight ask's morning answer was eaten exactly this way). The stall watchdog cross-checks the agent session's own stream activity (`AgentSession.lastStreamActivity`): a turn the agent is still streaming is never killed by an idle fire; a pump left blind by a degraded handoff logs a `blind pump` warning, and the shield expires once the stream itself has been silent for the whole idle window — a stream clock frozen newer than the pump's last receive cannot pin the session lock forever, and the orphan-pump start log names the first event it opened on. Progress-card stats ride the native session events: a tool result carrying the native failure identity marks its entry red and counts into 🔴调用失败, compaction lifecycle events increment the 🗜 count (falling back to a chat message when no preview card is active), and whole-list todo snapshots from any native producer replace the pinned todo section (a subagent child's list stays on its own card). CC_FEISHU_* workspace routing is injected as a system-prompt section through the D3 setup hook. Plain project-chat sessions always carry a fixed agent-conventions system-prompt section (async-autonomy work mode, curiosity reporting, a closing ask_user_question multi-select card over the reported findings, and a round-end one-line skillify offer); the engine's ask delegate recognizes that closing card by its prompt-mandated signature — a single question whose header is the reserved「后续处理」(the constant is shared with the prompt template, so the two cannot drift), or a single multi-select question offering a「暂不处理」option — and converts it instead of parking: the question is registered on the interactive state, the pre-ask reply segment is pinned onto the live-narration section right there (appendAnalysisText replaces the section per text block, so the post-ask trailing text would otherwise displace the closing summary off the card; the pin freezes it as a prefix that post-ask blocks append under, so the completed card carries the full reply like any other turn — a speculative digest render cannot stand in for it, because the render session is a one-screen overview by design and lands after the followups card; 2026-09-03 oc_f924a2), the ask returns a deferral notice as its tool result (so the turn ends normally and even a stale-prompt session stops waiting), and the ✅ completion card is followed by a blue followups suggestion card (checkboxes pre-checked from `recommended: true`, an in-form note input) whose `fw_multi:` submit composes a self-contained「[后续处理]」selection message flagged `isFollowupAction` — a flag the ask router never claims, so the selection starts a fresh turn even while another ask is parked on the session, and not clicking the card declines silently (an errored turn drops the registration; queued takeovers carry it to the final turn's completion; the submitted card freezes into its settled marks from a send-time cache, and a click after a daemon restart still reaches the agent — only the freeze is lost); plain sessions and subtask children both also carry the TDD-default section (default red-green-refactor discipline for implementing features, changing behavior, or fixing bugs, loop details left to the `tdd` skill); subtask children and chatroom personas omit the conventions — their findings surface through the parent session and their own personas. Unattended sessions (agent-delegated subtask children without a human, chatroom role / direct-role personas) auto-approve tool permissions and never enter plan mode — Go effectiveMode's bypassPermissions — while AskUserQuestion and plan cards still surface there (attended subtasks keep full approval; a chatroom moderator keeps the normal tool-approval path but likewise never enters plan mode — an inherited project plan default is downgraded at session start, the one deliberate deviation from Go effectiveMode). Cron prompt runs likewise never inherit a plan-mode project default: an unset job mode starts the run in `default` (an explicit job mode still applies), because no human is there to approve the ExitPlanMode card. Engine-woken turns (background job completion, background subagent report) run on an orphan-turn pump with the same delivery, approval bridging, and permission shielding as message turns. A plan-review rejection opens a discussion round instead of an immediate re-presentation: the bundle-patch plan-mode guidance (lockstep with dsh-base) has the model answer the feedback in its reply and end the turn — the answer rides the turn's final reply card at the chat tail — re-presenting only after the user asks for the updated plan (an explicit re-present request inside the rejection note counts as asking; otherwise a closing followups option offers the update), and the exit_plan_mode tool description stays mechanism-only so rejection policy lives solely in the deployment-owned section. A plan-review approval may carry a typed note; the supplement is steered into the running turn as a user message next to the approval tool result, because the review answer itself must stay `selected`-only (any `custom` reads as keep-planning feedback). A project configured `agent.planApprovalPreset` switches the approving session's permission preset through the composed permission-presets service at that same moment: the durable preset / sandbox-mode / approval-policy events take effect on the session's next confined call (a `danger-full-access` elevation grants the plan's execution full file access without approval prompts), while a deny, an unset field, or a missing preset service leaves permissions unchanged (the last logged as a misconfiguration). An ordinary-tool deny note rides the same steer channel verbatim — the approval seam carries outcomes only, so the wrapped native deny message is dropped downstream otherwise. A displacement heal keeps the active progress card at the chat tail — the sidebar summary only tracks the newest message, so the card must hold it for its in-place PATCHes to keep updating that summary. The platform keeps a per-chat activity ledger touched by every inbound message and every non-preview outbound send; on a content flush a card the ledger marks displaced reissues itself at the tail (create new, delete old) carrying that flush's content, so every recall tombstone also delivers fresh status. Card sends themselves stay exempt, so a reissue never displaces itself and concurrent preview cards cannot bump-loop; rename/avatar system notices touch the ledger through their im.chat.updated_v1 event — healed by the next content flush, with the debounced chat-changed push bump as the silent-run backstop (the card-header PATCH would otherwise race the notice's system message), and the bump is gated on the same ledger, so a card that already owns the tail (reissued past the notice, or living in an isolated thread) is not pointlessly recalled and resent; the turn-end baseline repaint fires after the terminal card render so its system message displaces a card that never reissues; thread-isolated cards never reissue (the root-chat tail is meaningless for them).

## Model Experience

### Request context and condition

#### What the model sees

This plugin never constructs LLM requests itself — every model input goes through the dsh agent layer (fully replayable from the session log), and all model-visible text the plugin contributes is conditionally injected and preserved verbatim from the Go original: the inbound prompt carries the user text, the reply-chain prefix (`[Quoted message from X]:` single-message form or `--- Reply chain (n messages) ---` numbered chain), staged-attachment path bullets, and `(Images saved locally, please read them: <paths>)` / `(Files saved locally, ...)` notes; projects with feishuWorkspace configured get a "default Feishu workspace" system-prompt section injected with the session through the setup hook (CC_FEISHU_* values + creation precedence; a chatroom bare persona replaces the system prompt wholesale and omits this section); a chatroom bare-persona session also calls `agentInstructions.suppress()`, so workspace instruction injection (AGENTS.md/CLAUDE.md reminders) never rides along on its user messages — Go `--bare` parity for disabled CLAUDE.md auto-discovery — and denies the global `skill` tool via `tools.restrict({ deny: ['skill'] })`, which removes the `<available_skills>` catalog and its loader with it; the plan/reply render fork pairs its complete system-prompt replacement with the same `agentInstructions.suppress()` while keeping its working tools (it denies only the global `skill` tool, dropping the `<available_skills>` catalog — the render skill body is baked into its system prompt), so workspace instructions stay off render requests — the fork's task facts travel only in its prompt (html_path plus the plan-markdown / plan-rendered-html block); both the render fork and every lightweight side query (group naming, predict-next, turn summary, monitor triage) are created with session origin `oneshot`, which keeps the cwd-derived memory index out of their user messages and LLM title generation off their throwaway sessions; a lightweight side query runs fully bare — a one-line complete system prompt replaces the assembled baseline and `tools.restrict({ allow: [] })` masks every tool — so its request is the prompt alone; a project configured with `mcpServers` (an MCP server-name allowlist, per-project MCP tool visibility) additionally denies every other server's `mcp__*` tools in the same setup hook — the mask covers plain sessions, resumes, forks, chatroom personas, and one-shot queries (a bare deny-all query folds the mask into its single restriction instead), and is forwarded as the `toolFilter` of every continuable subtask child (children do not inherit the parent's restrictions), pinned by `tests/agent-dsh/adapter-mcp-mask.spec.ts`; sibling plugins may register per-engine tool-name masks on the bridge service (`denyTools`), and the same setup hook denies those names from that project's sessions (forwards them to child `toolFilter`s the same way) — the chatroom plugin hides `feishu_bridge_chatroom` on projects configured `enabled: false`, so the definition leaves those projects' requests entirely; sibling plugins may likewise register per-engine skill-name masks on the bridge service (`denySkills`), which the same setup hook applies as a scoped `skills.restrict({ deny })` — the `<available_skills>` catalog, the `skill` loader, and the `/skills` listing all refuse those names for that project's sessions (denied skill names are not validated against a live catalog because skill availability is cwd-dependent; continuable subtask children are outside this mask, while their inherited `toolFilter` still denies the corresponding tools); an opt-in `mcpHealth` block registers a `feishu-bridge:mcp-health` runtime context that states, as one line per server, every configured server whose `mcp__<serverName>__*` tools are absent from the process-global tool registry after a startup grace period (with the configured `fixHint`), so a new session learns an MCP server is degraded before it tries the missing tools — the text is re-evaluated at each assembly and contributes nothing while every watched server has its tools registered; research-assistant children are coding agents and keep cwd instruction discovery like every other subtask child — their shared workspace defaults to `<projectDataDir>/chatroom-research` (configurable), off every chatroom persona's cwd-ancestor chain, so nothing contradicts their own preamble; every plain project-chat session additionally gets the non-Go prompt contributions, a fixed agent-conventions system-prompt section (`feishu-bridge-agent-conventions`, order 10: the async-autonomy work mode and chat-delivery rules, the curiosity-reporting contract, a closing ask_user_question multi-select card over the「发现的问题 / 可优化点」section whose prompt-mandated signature the engine converts into a non-blocking followups suggestion card (emitted after the ✅ completion card; submissions arrive as「[后续处理]」new-message turns), and the round-end skillify offer; subtask children and chatroom bare personas do not get it) plus the TDD-default section (`feishu-bridge-tdd-default`, order 20: the default red-green-refactor discipline for implementing features, changing behavior, or fixing bugs, loop details left to the `tdd` skill; plain sessions and subtask children both register it), both pinned verbatim by `tests/agent-dsh/adapter-persona.spec.ts`; the `feishu_bridge_subtask / cron / relay / lark / send` tool families register into the dsh tool catalog (the chatroom family from the sibling chatroom plugin), lark tool results are the lark-cli subprocess stdout/stderr verbatim, and `feishu_bridge_send` (the Go `cc-connect send` CLI's tool form) delivers local files to the user's chat as image/file messages through `Engine.sendToSessionWithAttachments`; chatroom bare personas carry the file-delivery section from Go `ChatroomRoleBaseSystemPrompt`, and subtask children append the report / no-report preamble (Go `buildAppendSystemPrompt`'s `CC_SUBTASK` branch) as a non-complete section.

#### Token effect

Conditional injection: every plain session carries the fixed agent-conventions section (a constant per-session prefix, roughly 1450 characters) plus the TDD-default section (roughly 360 characters), and subtask children carry the TDD-default section alone; chatroom personas replace the system prompt wholesale and get neither, so for them, with no attachments, no reply chain, and no workspace configured, the direct token cost is zero; render forks additionally drop workspace instructions (AGENTS.md/CLAUDE.md baseline), the memory index, and the skill catalog, so their input is the render system prompt plus the task prompt only; bare lightweight side queries reduce further to the one-line bare system prompt plus the query prompt (no tools, no catalog, no injections — a live naming query measured ~16.4k input tokens, over 95% of it injection the bare query drops); reply chains cap at 5 messages; attachment notes carry paths only, never bytes. A project with `mcpServers` configured removes every non-allowed MCP server's tool schemas from each of its model requests (schemas are per-request model input, so the saving recurs every step); MCP connections stay process-global — the mask is visibility only. Service-denied tool names (e.g. the chatroom tool on a chatroom-disabled project) leave that project's requests the same way, and service-denied skill names (e.g. the chatroom moderator skill on the same project) leave its `<available_skills>` catalog the same way. The `mcpHealth` context contributes zero tokens while every watched server is healthy; each degraded server adds one line per assembly.

#### KV Cache effect

Reply prefixes and attachment notes are appended inside each user message (append-only conversation prefix, cache-friendly); the agent-conventions, TDD-default, and workspace system-prompt sections are fixed per-session prefix segments, prefix-stable within a session; lark tool results enter the context once as tool messages and never rewrite history.

## Known Limitations and Deferred Work

- **The busy-session message queue is human-only and in-memory**: machine wakes (subtask reports, gather summaries, chatroom wakes, follow-up injections) reach a busy turn mid-turn via steer and never queue, so the queue's semantics — the 📬 queued-notice reply, the length cap (`queue.maxDepth`, default 5, dropping the overflow message), and in-memory storage — now bind human messages alone; a daemon restart between queueing and drain still loses those queued human messages. Cron prompts stay on the pipeline by design: their mode override, workDir switch, and new-session-per-run semantics need the full message path.
- **`mcpHealth` detection infers degradation from tool-registry presence, not connection state**: a watched server is "degraded" when no `mcp__<serverName>__*` tool is visible in the no-scope registry view, which cannot distinguish the cause (token expiry, connection failure, exhausted reconnects) and reports no precise degradation onset time (only "after the startup grace"). The enumeration assumes the mcp-client rows mount at profile root, so their registrations sit in the global tool layer; a server mounted inside an agent-scoped preset is invisible to the global view and reads as permanently degraded. A project's `mcpServers` visibility mask does not affect the check (it reads registration truth, not per-session visibility).
- **A masked MCP server that revives leaks into sessions created while it was down**: the deny mask is computed from the live tool view at session creation, and deny masks admit later-arriving unnamed globals — a server that reconnects after a session started adds its tools to that session's view until the next session start or resume recomputes the mask. `mcpServers` is also visibility composition, not an authority boundary, and a typo'd server name is indistinguishable from an outage (the server's tools are simply absent). Upgrade path: pattern-based restriction in core `tools` (see the per-project MCP visibility Agent Note).

- **The lark tool supports only the Feishu domain (open.feishu.cn)**: the plugin's platform side never ported Go `larkCreds.Brand` (the lark.com dual domain); introducing a brand dimension into `src/tools/lark.ts` and the platform client is the path when lark.com is needed.
- **The send tool reads local paths only**: Go's CLI also fetched http(s) URLs for `--image/--file`; agent artifacts live on disk, so the fetch branch is not ported. The i18n `relay_setup_ok`/`cron_setup_ok` messages remain ported-but-unwired residue: their Go callers write the CLI instructions into agent memory files, a path obsolete under dsh (every session has the native system-prompt mechanism).
- **Quoted-message sender names are not resolved**: the platform never resolves contact names through the directory API (a deliberate cut since M1); senders render as `User`/`Bot` in reply chains; add a `resolveUserName` cache on the platform when real names are needed.
- **`/learn` quoting works only on the event path**: monitored messages ingested by the polling fallback (`pollItemToMessage` builds them without parent/quote info) cannot back `/learn`'s quoted example; human `/learn` messages arrive over the WS event path and do carry the quote (monitored chats are exempt from the thread-isolation quote-fetch skip).
- **`reply_footer` (#11) balance segment is pending adapter growth**: the footer itself is wired (M7-b, `status-footer.ts` buildReplyFooter, default off); the usage/balance segment stays empty until the dsh adapter grows a UsageReporter (the capability seam is ready).
- **Inbound voice messages are dropped (ruled out)**: Go transcribed them via `[speech]` (Whisper-compatible providers); the TS platform drops `audio` messages by user ruling (2026-08-21 audit). The `voice_*` i18n strings are ported-but-unwired residue; porting `speech.go` is the upgrade path if voice input is ever needed.
- **Agent failures surface raw and unclassified (ruled out)**: Go's failure_classify.go (seven error classes driving user-facing text) plus redact/ (secret scrubbing before display) are not ported, per the same ruling; the raw error text reaches the chat.
- **Card button callbacks cannot be tested automatically**: `card.action.trigger` can only be verified by real-device clicks (the Feishu platform has no callback-simulation API); button paths are covered by pure-function table tests plus real-device smoke runs.
- **Multi-workspace is not migrated**: the channel→workspace binding (Go workspace_binding.go) and the per-workspace agent pool are not wired; single workspace + `/dir` per-chat override carries production needs, classified C in the group-E audit.
- **A fork whose source is gone degrades silently**: the seed resolves live-first, then from the sessionPersistence log (a merely-persisted parent — after a daemon restart or idle reap — still forks, matching Go's on-disk read); a parent with a flying turn seeds too — the in-flight turn is cut at its last balanced point (dangling tool calls settled with the runtime's AbortError result shape) and closed with synthetic `step/end` + `turn/end(interrupted)` (`agent-dsh/fork-seed.ts`, extending Go's completed-turns-only copy); only when the source is nowhere, or holds nothing seedable, does the fork start a fresh session with a log warn and no chat message.
- **`nav:/help` buttons are inert**: the cron card's back button targets Go's help-card system (`renderHelpGroupCard` + the `nav:` help navigation), which is not ported; the click reaches the engine and logs "no handler" instead of silently vanishing. Porting the help-card family is the fix; the `/dir` picker card ships without a back button for the same reason.
- **Displacement heal rides content flushes, with known boundaries**: the heal runs on the preview's own throttled flush cycle, so a displaced card re-takes the tail when its next status change lands — during a silent tool run the sidebar keeps showing the displacer, which is itself the newest information; displacement classes the ledger never sees (system messages other than chat rename/avatar) stay unhealed until the next tracked activity; the chat-changed bump shares the ledger gate, and its event timestamp only approximates the notice's landing moment — a card reissued inside the webhook lag between the two still takes one extra reissue; the legitimate reissue tombstone count equals the displacement count, because Feishu offers no reorder primitive besides recall+resend — the turn-end avatar repaint no longer contributes (it paints after the terminal card render), leaving rare attention repaints (stall, dead subtask child) and mid-turn messages as the re-take sources; two streaming bots in one chat would still reissue over each other (no such topology exists today).
- **`/list`, `/status`, and `/switch` remain plain-text surfaces**: Go renders `renderListCardSafe`/`renderStatusCard` cards with `act:/list switch|delete N` actions; the TS commands keep their text output until that render domain is ported.
- **The Go command inventory is intentionally partial**: `/shell` + `!`, `/tag`, `/untag`, `/undone`, `/notify`, `/board`, `/help`, and `/ps` landed (Agent Notes `feature/2026-08-20-feishu-bridge-shell-command.md` and `feature/2026-08-20-feishu-bridge-seven-commands.md`); TS-native additions are `/reload` (runs reload.sh detached for admins, see OPERATIONS.md §3.3; not a port of Go's `/restart`), `/skills` + `/mcp` (read-only listings of the runtime skill catalog for the chat's work dir and of live MCP servers, with degraded and allowlist-masked markers; no Go counterpart), and `/context` (a context-insight card from the live session's projections: occupancy headline, six-bucket composition and per-turn trend as native chart elements, recent context events, session statistics, and the top tool schemas, with an in-place refresh button; degrades to the token-meter headline when dsh-context is not mounted and to a friendly empty card when no agent session is live); `/help` generates its list from the registered handlers, so it cannot drift. The remaining ~27 of Go's 53 builtin commands are a deliberate curation (user ruling 2026-08-21): upgrade/restart/web/doctor/version are D-class cuts, and the rest (`/whoami`, `/history`, `/current`, `/search`, `/delete`, `/name`, `/memory`, `/model`, `/reasoning`, `/mode`, `/lang`, `/quiet`, `/tts`, `/allow`, `/config`, `/show`, `/diff`, …) stay unported by design; `/tts` additionally depends on the pending voice-capability ruling.
