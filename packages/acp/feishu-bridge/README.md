# dsh-feishu-bridge

English | [中文](README.zh.md)

cc-connect's orchestration capability (engine + Feishu platform) migrated into dsh as a single plugin: one long-lived dsh process assembles, per configured project, an Engine plus a Feishu WS platform (official node-sdk long connection, D5); agent sessions are created natively through `ctx.agents`, with no bridge protocol left. The migration plan, milestones, and decision records live in [docs/MIGRATION.md](docs/MIGRATION.md); the 61-item feature comparison in [docs/FEATURE-PARITY.md](docs/FEATURE-PARITY.md); deployment and configuration mapping in [docs/OPERATIONS.md](docs/OPERATIONS.md).

Plugin structure:

| Directory | Contents |
|---|---|
| `src/engine/` | faithful port of Go `core/`: the event state machine, sessions, commands, cron, relay, chatroom, monitor, i18n, attachment staging |
| `src/feishu/` | port of Go `platform/feishu/`: WS, API client, cards, progress cards, chat management, tags, avatars, media, quoted-message fetching |
| `src/agent-dsh/` | Agent interface → `ctx.agents` adapter (D1/D3: setup hooks, provider routing, approval/question/plan wiring) |
| `src/tools/` | the `feishu_bridge_subtask / cron / relay / chatroom / lark / send` tool families (D4: caller-agent routing, no env needed); the lark tool registers as `lark-cli` — named verbatim after the official CLI so every command reference in lark-cli's embedded skills maps literally to a tool call, and its description routes domain tasks through `skills list` / `skills read` |
| `skills/` | bridge skills (`feishu-bridge-` prefix) plus the deployment's working-style skills (`tdd`, `skillify`), auto-mounted as an isolated skill provider by `apply()` — no `customSkillDirs` wiring needed |

Native subtasks (de-baggage B4): the profile's `dsh-base` bundle mounts `SubagentRuntime` (with `settlementNotice: 'external'`, overridden via this bundle's patch) plus the in-process spawn/fork providers, so unattended `feishu_bridge_subtask` spawns run as native continuable child sessions — no Feishu group — with lineage, depth, and cold resume owned by the native runtime; the engine keeps only the parentage record (persisted in the project state, surviving restarts) and the worktree it created. Settlement reaches the engine through the `subagent/end` listener: a child that never explicitly reported still delivers its final assistant output through the same card + `[子任务完成]` wake as the group path, and a follow-up's answer re-arms that delivery. The settlement text carries the terminal outcome — a non-completed stop reason prefixes failure semantics (error / max-tokens / refusal / aborted, plus the provider diagnostic and a no-closing-output notice when the epoch left none), so failed work never reports as finished. `gather` is the synchronous delivery contract: the call blocks until every in-flight child reports or the gather timeout (default 20 minutes) returns a partial summary naming the missing, and the summary lands as the call's own result in the still-open parent turn — child tool activity streams on its live card while the call is in flight, and an aborted wait (user stop) falls back to the per-report wake. The expected set holds only children that can settle the barrier (subtask-depth sessions and native children); chatroom role groups hanging off the hub are excluded — their replies settle through the chatroom relay — and a parent with no gatherable child fails fast instead of arming a timeout-bound barrier. `send` queues behind the child's running turn (the deliberate deviation from Go's busy-reject), `interrupt` stops the current turn without disposing the child, and `/done` / chatroom end drain native descendants (interrupt + clean-worktree recycle). A drained worktree whose only dirty cause is commits already contained in its containment target — as ancestors or patch-equivalent after a rebase — is removed automatically instead of being kept; the target defaults to the branch HEAD was on when the worktree was created (per-repo, zero config), with `spawn.integrateBranch` as a global override. Uncommitted changes and unmerged commits always keep the worktree (the group path keeps them for the per-child Keep/Remove card); a detached or unknown creation-time base branch leaves auto-removal off for that worktree. Attended groups (`/spawn`, monitor children, chatroom pre-spawned assistants) keep the group path unchanged, and group-path children gained the matching failure notices: an error-reasoned turn auto-reports with the failure and its own partial streamed text (never a stale earlier reply), a mid-turn process exit reports the partial output with an interruption prefix, and terminal cleanup paths (stall kill, hard turn cap, dead-agent send failure) deliver the synthetic timeout notice so the parent never waits forever. `features.subtaskQuiet: true` suppresses the settlement card for unattended native subtasks — the result reaches the parent agent context through the wake only, matching the generic `subagent` tool's silent return; attended group children and monitor chats keep their cards either way. Unreported native children stay visible while they run: a spawning turn shows a `subtasks_running_hint` line beside the stop button, and every settled card title appends `· N 个子任务运行中` (plus the body hint and the same line on the ✅ completion push), the count recomputed from the persisted records at each render — the header itself stays terminal, because the parent turn really did end. A spawned group's avatar background is a five-color lifecycle signal: yellow while no plan is approved (discussion, direct work, never-planning runs alike), blue while an ExitPlanMode card is parked, green once approved, red when the user must step in (a pending question/permission card, an errored turn, a stall timeout), gray after `/done`; same-color transitions are deduplicated so each Feishu avatar-update system message marks a real state change, and chatroom families / branded hubs keep name-hashed colors outside the signal ([Agent Note](../../.agents/notes/implemented/feature/2026-08-26-feishu-bridge-lifecycle-phase-avatar.md)).

Model-visible surface: inbound messages (with reply-chain prefixes and staged-attachment path notes) enter the prompt; outbound goes through the card system (progress cards, completion cards, approval cards). A turn that ends with an error reason (for example a provider content-moderation rejection) finalizes the progress card as 执行失败 with the error text replacing the live-narration section, records the error as the turn's reply, and sends it as a plain message when no preview card is active; interim narration between tool calls never stands in as the final answer. Every turn exit renders a terminal card: user and engine stops land the ⏹ stopped card whether the event loop drains the stop arm, a channel close racing the stop, or a plugin reload; stall retries retire the stalled card as failed and abnormal agent exits fail the card; late Running PATCHes after a stopped render are dropped. late Running PATCHes after a stopped render are dropped. Engine stop additionally fires the state's stop signal, so an ask parked on card delivery settles cancelled instead of hanging on a stopped platform — the parked tool call can never outlive the engine and leak the session live in the persistence coordinator. The stall watchdog cross-checks the agent session's own stream activity (`AgentSession.lastStreamActivity`): a turn the agent is still streaming is never killed by an idle fire; a pump left blind by a degraded handoff logs a `blind pump` warning, and the shield expires once the stream itself has been silent for the whole idle window — a stream clock frozen newer than the pump's last receive cannot pin the session lock forever, and the orphan-pump start log names the first event it opened on. Progress-card stats ride the native session events: a tool result carrying the native failure identity marks its entry red and counts into 🔴调用失败, compaction lifecycle events increment the 🗜 count (falling back to a chat message when no preview card is active), and whole-list todo snapshots from any native producer replace the pinned todo section (a subagent child's list stays on its own card). CC_FEISHU_* workspace routing is injected as a system-prompt section through the D3 setup hook. Plain project-chat sessions always carry a fixed agent-conventions system-prompt section (async-autonomy work mode, curiosity reporting, and a closing ask_user_question multi-select card over the reported findings, options ordered by recommendation with `recommended: true` options pre-checked); subtask children and chatroom personas omit it — their findings surface through the parent session and their own personas. Unattended sessions (agent-delegated subtask children without a human, chatroom role / direct-role personas) auto-approve tool permissions and never enter plan mode — Go effectiveMode's bypassPermissions — while AskUserQuestion and plan cards still surface there (attended subtasks keep full approval; a chatroom moderator keeps the normal tool-approval path but likewise never enters plan mode — an inherited project plan default is downgraded at session start, the one deliberate deviation from Go effectiveMode). Cron prompt runs likewise never inherit a plan-mode project default: an unset job mode starts the run in `default` (an explicit job mode still applies), because no human is there to approve the ExitPlanMode card. Engine-woken turns (background job completion, background subagent report) run on an orphan-turn pump with the same delivery, approval bridging, and permission shielding as message turns. A plan-review approval may carry a typed note; the supplement is steered into the running turn as a user message next to the approval tool result, because the review answer itself must stay `selected`-only (any `custom` reads as keep-planning feedback). An ordinary-tool deny note rides the same steer channel verbatim — the approval seam carries outcomes only, so the wrapped native deny message is dropped downstream otherwise. A preview tail guard keeps the active progress card the chat's newest message: every `streamPreview.tailCheckMs` (default 5000, 0 disables) the card verifies it still holds the tail and reissues itself above whatever displaced it — engine cards, human messages, member/avatar system notices, other bots, manual sends — so the sidebar thumbnail keeps reflecting header changes without opening the chat; the rename/avatar push bump stays as the fast path, and thread-isolated cards skip the guard (the root-chat tail is meaningless for them).

## Model Experience

### Request context and condition

#### What the model sees

This plugin never constructs LLM requests itself — every model input goes through the dsh agent layer (fully replayable from the session log), and all model-visible text the plugin contributes is conditionally injected and preserved verbatim from the Go original: the inbound prompt carries the user text, the reply-chain prefix (`[Quoted message from X]:` single-message form or `--- Reply chain (n messages) ---` numbered chain), staged-attachment path bullets, and `(Images saved locally, please read them: <paths>)` / `(Files saved locally, ...)` notes; projects with feishuWorkspace configured get a "default Feishu workspace" system-prompt section injected with the session through the setup hook (CC_FEISHU_* values + creation precedence; a chatroom bare persona replaces the system prompt wholesale and omits this section); a chatroom bare-persona session also calls `agentInstructions.suppress()`, so workspace instruction injection (AGENTS.md/CLAUDE.md reminders) never rides along on its user messages — Go `--bare` parity for disabled CLAUDE.md auto-discovery — and denies the global `skill` tool via `tools.restrict({ deny: ['skill'] })`, which removes the `<available_skills>` catalog and its loader with it; the plan/reply render fork pairs its complete system-prompt replacement with the same `agentInstructions.suppress()` while keeping its working tools (it denies only the global `skill` tool, dropping the `<available_skills>` catalog — the render skill body is baked into its system prompt), so workspace instructions stay off render requests — the fork's task facts travel only in its prompt (html_path plus the plan-markdown / plan-rendered-html block); both the render fork and every lightweight side query (group naming, predict-next, turn summary, monitor triage) are created with session origin `oneshot`, which keeps the cwd-derived memory index out of their user messages and LLM title generation off their throwaway sessions; a lightweight side query runs fully bare — a one-line complete system prompt replaces the assembled baseline and `tools.restrict({ allow: [] })` masks every tool — so its request is the prompt alone; a project configured with `mcpServers` (an MCP server-name allowlist, per-project MCP tool visibility) additionally denies every other server's `mcp__*` tools in the same setup hook — the mask covers plain sessions, resumes, forks, chatroom personas, and one-shot queries (a bare deny-all query folds the mask into its single restriction instead), and is forwarded as the `toolFilter` of every continuable subtask child (children do not inherit the parent's restrictions), pinned by `tests/agent-dsh/adapter-mcp-mask.spec.ts`; an opt-in `mcpHealth` block registers a `feishu-bridge:mcp-health` runtime context that states, as one line per server, every configured server whose `mcp__<serverName>__*` tools are absent from the process-global tool registry after a startup grace period (with the configured `fixHint`), so a new session learns an MCP server is degraded before it tries the missing tools — the text is re-evaluated at each assembly and contributes nothing while every watched server has its tools registered; research-assistant children are coding agents and keep cwd instruction discovery like every other subtask child — their shared workspace defaults to `<projectDataDir>/chatroom-research` (configurable), off every chatroom persona's cwd-ancestor chain, so nothing contradicts their own preamble; every plain project-chat session additionally gets the one non-Go prompt contribution, a fixed agent-conventions system-prompt section (`feishu-bridge-agent-conventions`, order 10: the async-autonomy work mode and chat-delivery rules, the curiosity-reporting contract, and a closing ask_user_question multi-select card over the「发现的问题 / 可优化点」section; subtask children and chatroom bare personas do not get it), pinned verbatim by `tests/engine/chatroom-persona.spec.ts`; the `feishu_bridge_subtask / cron / relay / chatroom / lark / send` tool families register into the dsh tool catalog, lark tool results are the lark-cli subprocess stdout/stderr verbatim, and `feishu_bridge_send` (the Go `cc-connect send` CLI's tool form) delivers local files to the user's chat as image/file messages through `Engine.sendToSessionWithAttachments`; chatroom bare personas carry the file-delivery section from Go `ChatroomRoleBaseSystemPrompt`, and subtask children append the report / no-report preamble (Go `buildAppendSystemPrompt`'s `CC_SUBTASK` branch) as a non-complete section.

#### Token effect

Conditional injection: every plain session carries the fixed agent-conventions section (a constant per-session prefix, roughly 1100 CJK characters); chatroom personas replace the system prompt wholesale and subtask children never get it, so for them, with no attachments, no reply chain, and no workspace configured, the direct token cost is zero; render forks additionally drop workspace instructions (AGENTS.md/CLAUDE.md baseline), the memory index, and the skill catalog, so their input is the render system prompt plus the task prompt only; bare lightweight side queries reduce further to the one-line bare system prompt plus the query prompt (no tools, no catalog, no injections — a live naming query measured ~16.4k input tokens, over 95% of it injection the bare query drops); reply chains cap at 5 messages; attachment notes carry paths only, never bytes. A project with `mcpServers` configured removes every non-allowed MCP server's tool schemas from each of its model requests (schemas are per-request model input, so the saving recurs every step); MCP connections stay process-global — the mask is visibility only. The `mcpHealth` context contributes zero tokens while every watched server is healthy; each degraded server adds one line per assembly.

#### KV Cache effect

Reply prefixes and attachment notes are appended inside each user message (append-only conversation prefix, cache-friendly); the agent-conventions and workspace system-prompt sections are fixed per-session prefix segments, prefix-stable within a session; lark tool results enter the context once as tool messages and never rewrite history.

## Known Limitations and Deferred Work

- **`mcpHealth` detection infers degradation from tool-registry presence, not connection state**: a watched server is "degraded" when no `mcp__<serverName>__*` tool is visible in the no-scope registry view, which cannot distinguish the cause (token expiry, connection failure, exhausted reconnects) and reports no precise degradation onset time (only "after the startup grace"). The enumeration assumes the mcp-client rows mount at profile root, so their registrations sit in the global tool layer; a server mounted inside an agent-scoped preset is invisible to the global view and reads as permanently degraded. A project's `mcpServers` visibility mask does not affect the check (it reads registration truth, not per-session visibility).
- **A masked MCP server that revives leaks into sessions created while it was down**: the deny mask is computed from the live tool view at session creation, and deny masks admit later-arriving unnamed globals — a server that reconnects after a session started adds its tools to that session's view until the next session start or resume recomputes the mask. `mcpServers` is also visibility composition, not an authority boundary, and a typo'd server name is indistinguishable from an outage (the server's tools are simply absent). Upgrade path: pattern-based restriction in core `tools` (see the per-project MCP visibility Agent Note).

- **The lark tool supports only the Feishu domain (open.feishu.cn)**: the plugin's platform side never ported Go `larkCreds.Brand` (the lark.com dual domain); introducing a brand dimension into `src/tools/lark.ts` and the platform client is the path when lark.com is needed.
- **The send tool reads local paths only**: Go's CLI also fetched http(s) URLs for `--image/--file`; agent artifacts live on disk, so the fetch branch is not ported. The i18n `relay_setup_ok`/`cron_setup_ok` messages remain ported-but-unwired residue: their Go callers write the CLI instructions into agent memory files, a path obsolete under dsh (every session has the native system-prompt mechanism).
- **Quoted-message sender names are not resolved**: the platform never resolves contact names through the directory API (a deliberate cut since M1); senders render as `User`/`Bot` in reply chains; add a `resolveUserName` cache on the platform when real names are needed.
- **`/learn` quoting works only on the event path**: monitored messages ingested by the polling fallback (`pollItemToMessage` builds them without parent/quote info) cannot back `/learn`'s quoted example; human `/learn` messages arrive over the WS event path and do carry the quote (monitored chats are exempt from the thread-isolation quote-fetch skip).
- **`reply_footer` (#11) balance segment is pending adapter growth**: the footer itself is wired (M7-b, `status-footer.ts` buildReplyFooter, default off); the usage/balance segment stays empty until the dsh adapter grows a UsageReporter (the capability seam is ready).
- **Inbound voice messages are dropped (ruled out)**: Go transcribed them via `[speech]` (Whisper-compatible providers); the TS platform drops `audio` messages by user ruling (2026-08-21 audit). The `voice_*` i18n strings are ported-but-unwired residue; porting `speech.go` is the upgrade path if voice input is ever needed.
- **Agent failures surface raw and unclassified (ruled out)**: Go's failure_classify.go (seven error classes driving user-facing text) plus redact/ (secret scrubbing before display) are not ported, per the same ruling; the raw error text reaches the chat.
- **Card button callbacks cannot be tested automatically**: `card.action.trigger` can only be verified by real-device clicks (the Feishu platform has no callback-simulation API); button paths are covered by pure-function table tests plus real-device smoke runs.
- **Multi-workspace is not migrated**: the channel→workspace binding (Go workspace_binding.go) and the per-workspace agent pool are not wired; single workspace + `/dir` per-chat override carries production needs, classified C in the group-E audit.
- **A fork whose source is gone degrades silently**: the seed resolves live-first, then from the sessionPersistence log (a merely-persisted parent — after a daemon restart or idle reap — still forks, matching Go's on-disk read); only when the source is nowhere does the fork start a fresh session with a log warn and no chat message.
- **Chatroom picker state is in-memory**: a daemon restart drops the armed pickers; the next click on an orphaned pick card swaps it in place for a grey expired card prompting a fresh `/chatroom` (Go left the orphan buttons silent or fake-confirming); remaining M7 domains (plan-render/usage/predict-next) advance per the MIGRATION.md queue.
- **`nav:/help` buttons are inert**: the cron card's back button targets Go's help-card system (`renderHelpGroupCard` + the `nav:` help navigation), which is not ported; the click reaches the engine and logs "no handler" instead of silently vanishing. Porting the help-card family is the fix; the `/dir` picker card ships without a back button for the same reason.
- **Preview tail guard heals per period, with known boundaries**: the guard converges on a period (`streamPreview.tailCheckMs`, default 5s) rather than reacting to events — displacement to reissue takes at most one period (chatroom ask/relay cards are now await-ordered and engine bump routing is per-session, so those two highest-frequency scenarios no longer lean on the guard; a card the user manually recalled is retired via `recalled_v1` instead of resurrected); thread-isolated deployments skip the guard; two streaming bots in one chat would reissue over each other (no such topology exists today).
- **`/list`, `/status`, and `/switch` remain plain-text surfaces**: Go renders `renderListCardSafe`/`renderStatusCard` cards with `act:/list switch|delete N` actions; the TS commands keep their text output until that render domain is ported.
- **The Go command inventory is intentionally partial**: `/shell` + `!`, `/tag`, `/untag`, `/undone`, `/notify`, `/board`, `/help`, and `/ps` landed (Agent Notes `feature/2026-08-20-feishu-bridge-shell-command.md` and `feature/2026-08-20-feishu-bridge-seven-commands.md`); a TS-native `/reload` additionally runs reload.sh detached for admins (see OPERATIONS.md §3.3; not a port of Go's `/restart`); `/help` generates its list from the registered handlers, so it cannot drift. The remaining ~27 of Go's 53 builtin commands are a deliberate curation (user ruling 2026-08-21): upgrade/restart/web/doctor/version are D-class cuts, and the rest (`/whoami`, `/history`, `/current`, `/search`, `/delete`, `/name`, `/memory`, `/model`, `/reasoning`, `/mode`, `/lang`, `/quiet`, `/tts`, `/allow`, `/config`, `/show`, `/diff`, …) stay unported by design; `/tts` additionally depends on the pending voice-capability ruling.
