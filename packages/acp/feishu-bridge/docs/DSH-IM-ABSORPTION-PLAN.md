## 0. 一句话结论

**本次吸收不改功能，只做三类事：把「说完成」与「真送达」对齐（批次 1）、两项用户已拍板的呈现优化（批次 2）、状态持久化与信任边界加固（批次 3）。** 对照文档的北极星原则贯穿全部三批——投递结果必须回灌到用户可见状态。

## 1. 改什么、不改什么（已确认的边界）

**全程不变**：

- agent 能力、命令集、工作流、配置方式；
- 正常对话路径下的行为表现（批次 1/3 全部只在故障路径上起作用）。

**用户已拍板保留的呈现变化**（批次 2）：工具/状态行单行替换、思考心跳（默认开、配置可关）；换卡规则因对抗性核实未确认痛点存在，**改为先核实再实施**（见 §4.2）。

**计划批准即拍板的两个安全决策**（对照文档 §7.2 标记「待拍板」，推荐采纳）：

1. **审批批准人身份绑定**——现状默认配置下同群任一用户都能批准，且「全部允许」是 agent 生命周期常驻许可而非一次性（`user-approval/index.ts:165,250`）；单人使用无影响，群内有第三人（chatroom 场景）则是真实边界。
2. **审批词表收紧**——现词表含「好/好的/可以/是/ok/y」（`permission.ts:16-29`），等待审批期间一条恰好等于这些词的普通聊天会被当成批准。

**bridge 已更强、明确不回退的面**（对照文档 §5.4/§7.4/§8.3/§9.2，防止反向「优化」）：

- 追问卡体系：闭卡签名识别、非阻塞注册 + deferred 决策、卡+快照+提交消息三件套、**跨重启持久化 FollowupsMetaStore（7 天）**——dsh-im 无等价物；
- plan 审批流深度（分层审批 + 权限 preset 联动）；
- `PermissionExpired` / `AskqStaleCard` 分离的失败语义；
- 230020 限流处理（已判 transient 且不计入降级计数，dsh-im 对应文件反而无错误码感知）；
- 节流/抖动合并/终态前排空在途 PATCH 体系；
- pending inbox 跨 daemon 重启不丢（已是一种延迟投递）；
- 分层：中性 Platform 接口 + 101 能力接口 + 64 守卫 + 中性卡 IR，`engine → feishu/` 仅 2 处 import；
- StreamPreview 状态机（2000+ 行、60+ 方法）不重写、不迁移 CardKit。

## 3. 核心结论：三个已核实缺口

对照文档 §0 的三个真实缺口是本次吸收的靶心：

1. **说完成但可能没送达**：发送失败只 `console.debug`（`engine.ts:1911-1926`）或 `console.warn`（`streaming.ts:1768`）；终态只看 `errorText`（`engine.ts:3987`），进度卡照常 finalize 绿（`feishu/progress.ts:141-144`）、完成卡照发（`engine.ts:4198-4227`）；最坏情形降级兜底 `fallbackSend` **先删冻结卡再投递**（`streaming.ts:1778-1788`），失败则卡片消失且答案彻底收不到。
2. **重试可能重复发**：飞书 `im/v1` create/reply 支持 uuid 幂等去重（SDK 类型 `types/index.d.ts:264216-264222`）但本插件从不传（`platform.ts:3638-3651`）；可重试集合含桥自己合成的 `context deadline exceeded`（`retry.ts:17-23,126-132,156-158`，maxRetries=3 共 4 次尝试）——超时时请求可能已投递成功。
3. **超时直接丢答案**：stall 耗尽（`engine.ts:3398-3413`）与硬帽（`:3432-3447`）两条路径都直接 return，不经过任何投递点；文本只剩卡面播报且截到 6000 字（`streaming.ts:49,2054-2064`）；通告口径反向引导重发（`i18n/messages.ts:277-278`），白烧一遍 token。

## 6. 验收与部署约定

- **全程 TDD**：每项先写失败测试再实现；审批词表负例、`../` 穿越负例、三态五类错误形态、两条强杀路径分片投出为必测。

- **Agent Note**：非平凡改动同批补 Agent Note；换卡 spike 结论、uuid 真机验证证据记录在案。
